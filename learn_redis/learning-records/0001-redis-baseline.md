# 起点：Redis 只会 SET/GET，目标是落地而非面试

用户在 2026-09-29 首次建立本工作区时自评：Redis **只会 SET/GET**，对其它数据结构、过期与内存淘汰机制「不清楚」。这一档位意味着**不能假设**任何关于 Hash / List / Set / ZSet / SCAN / 淘汰策略的既有认知——第 1 课必须从「Redis 是数据结构服务器，key 是设计对象」这一层心智模型建起。

同时确认了三件影响后续排课的事实：

- 动机是**落地到工作中的系统**，不是找工作。因此举例与练习要围绕生产事故、排查与取舍，避免八股问答式的内容。
- 优先级为 ① 数据结构与建模 ② 缓存模式与一致性 ③ 分布式原语；**主动未选**高可用与扩展（主从 / 哨兵 / Cluster），已写入 `MISSION.md` 的 Out of scope。
- 本地可跑 Docker，练习可以设计成**真实敲 `redis-cli`**，反馈循环能做成「命令 + 预期输出」的可自查形式，不需要退化成纸面推演。

## Evidence
用户在课程开始前的四选一/多选问卷中明确选择：「落地到工作中的系统」「只会 SET/GET 这一档」「数据结构与建模 / 缓存模式与一致性 / 分布式原语」「可装 Docker / 本地 Redis」。

## Implications
- 第 1 课的范围必须收窄到**一个决策**，不能同时讲多个数据结构。
- 「过期 vs 淘汰」「写命令是否重置 TTL」这类区分，属于典型的高频生产误区，值得在起点就作为主线，因为它们是所有缓存课程的地基。
- 若后续用户表现出对集群/高可用的兴趣，需要先**确认并更新 MISSION**，再变更排课。
