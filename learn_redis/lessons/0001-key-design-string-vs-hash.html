一个 key 该存什么

这节课只练一个动作：给每个缓存键做两个决定——用哪种数据结构、给不给 TTL。今天只处理 String 和 Hash 两个结构。能独立做出这两个决定，你就不会写出「内存只增不减」的缓存。

1为什么第一课讲这个

你现在的工具箱里只有 SET / GET——这几乎是每个 Redis 使用者的起点，但也是「出事故」的重灾区。最常见的两种线上事故，都发生在这一个决定上：

事故模板 A · 内存只增不减

缓存值写了不设过期，或者后续某次覆盖把 TTL 清掉了，于是所有 key 变成永久键，内存逐日上涨，直到实例写不进去。

事故模板 B · 一个对象拆成十个 key

把「用户档案」的每个字段各存一个 String key（user:1:name、user:1:email…）。读一次资料要 10 次网络往返，十个 key 的过期节奏也没法统一管理。

这两个事故的共同点是：它们不是「Redis 不懂」，而是写 key 时没做「存储建模」。Redis 官方的自我定义是 "Redis is a data structure server"（Redis 是一台数据结构服务器）官方——这句看着像废话，其实在说：你要设计的是「这台服务器里放哪种结构、键叫什么、活多久」，而不是「塞个值进去」。

2第一个决定：String 还是 Hash

先看清两种结构的差别：

StringHash
单位 一个 key ↔ 一个值 一个 key ↔ 一组「字段:值」
只想读一部分 不行，GET 只能整块拿 HMGET 只取指定字段
只想改一部分 得先读出整块、改完、再整块写回 HSET 直接改单个字段
过期粒度 整块（String 没有字段概念） 整个 key；字段级过期仅 7.4+（HEXPIRE）
典型用法 计数器、登录态 token、整块快照 对象型数据（用户档案、订单详情）
关键结论

对象型、字段多、常按字段局部读写 → Hash；单值、整读整写 → String。

用 String 存 JSON 是合法的，但它把「改一个字段」变成「整块序列化再覆盖」——多一次网络往返、有并发丢更新的风险，而且覆盖时很容易顺手把 TTL 清掉（下一节就是这件事）。

判断手法只有两个问题：「读的时候要整块还是要其中几个字段？」「写的时候是整体换还是只改一部分？」——等下节课选 ZSet / List 时，你会用同一套问题。

3第二个决定：TTL 给不给、怎么给

缓存默认不该永生。经验法则：凡是业务上能说清「这份数据多久之后不再可信」的，就写死 TTL。

时机命令场景
写入时就定（相对） SET k v EX 300 一次写入的缓存，最常见
写入时就定（绝对） SET k v EXAT 1735689600 「全站统一到某个时间点失效」
给已有 key 补上 EXPIRE k 300 写入时忘了，或需要动态续期
Hash 字段级（仅 7.4+） HEXPIRE h 300 FIELDS 1 f1 一个 Hash 里混了长短命字段
本课最该记住的一条规则

官方原文：TTL 只会被删除或整体覆盖内容的命令清掉（DEL、SET、GETSET、所有 *STORE）；而原地改值的命令不会动 TTL。官方

翻译成人话：

  • SET 一个已有 key → 原来设的 TTL 没了（除非带上 KEEPTTL）。
  • HSET 更新 Hash 里的字段 → TTL 照旧。
  • 「每次访问自动续期」不会发生——想续期得自己再调一次 EXPIRE。

第四条也顺带记住：TTL 命令返回正数=还剩多少秒、-1=key 在但没有 TTL（＝永久键）、-2=key 不存在。完整对照在过期速查卡里，那是张以后会一直回来翻的卡。

4别把「过期」和「淘汰」搞混

这两个词都会让 key 消失，但完全不同：

  • 过期expiration · 你定 你给 key 设了 TTL，倒计时到点它就没了。这是你写代码决定的，跟内存多少无关。
  • 淘汰eviction · Redis 定 实例内存超过 maxmemory，Redis 按 maxmemory-policy（默认 noeviction）自行踢掉 key。这跟你的业务语义无关。

判据一句话：淘汰是「内存不够了」，过期是「时间到了」。排查时看 INFO stats——evicted_keys 高说明是淘汰（该加内存或调策略），expired_keys 高说明是 TTL 设太短。这是两个完全不同的问题，别找错方向。

5动手练习：给订单详情设计缓存

练习 · 必须真敲 redis-cli

需求（仿真）

你们的服务提供「订单详情」接口，一次返回一个订单的全部约 12 个字段。该接口被高频查询，而订单状态会变化。请用 Redis 为它设计缓存。

要输出的四个答案

  1. 结构：订单详情该用 String（整块 JSON）还是 Hash？写出理由。
  2. 键名：按「业务:实体:id」的约定写出键名。
  3. TTL：给一个你认为合理的过期时间，并说明依据。
  4. 验证：敲下面这组命令，把每行 TTL 的实际输出与注释里的期望值对一遍。

在 redis-cli 里执行（可整段复制）

DEL demo:order                 # 清干净，保证可重复

# A. String：SET 会把 TTL 清掉
SET demo:order json-v1 EX 300
TTL demo:order                 # 期望 300 附近 —— 有 TTL
SET demo:order json-v2
TTL demo:order                 # 期望 -1      —— TTL 被这次 SET 清掉了！

# B. Hash：HSET 不会清 TTL
DEL demo:order
HSET demo:order status PAID amount 1999
EXPIRE demo:order 300
TTL demo:order                 # 期望 300 附近 —— 有 TTL
HSET demo:order status SHIPPED
TTL demo:order                 # 期望 300 附近 —— HSET 没动 TTL

# C. 反向操作
PERSIST demo:order
TTL demo:order                 # 期望 -1      —— 变回永久键
参考答案（先自己写完再展开）

① 结构：推荐 Hash——字段多（12 个），而状态变更只需改 status 一个字段；Hash 能 HSET 局部更新，也能 HMGET 只取需要的字段，不必整块重写。

② 键名：order:8801:detail（业务:实体:id）。

③ TTL：数字本身不是重点，重点是依据——例如订单已完结，缓存留 1 小时足够：EX 3600。要能回答「为什么不设 10 分钟 / 为什么不设 1 天」。

④ 验证：A 段你会亲眼看见 -1 出现，这就是「TTL 被自己写没了」；B 段证明 Hash 的原地更新不影响 TTL。两段合起来就是事故模板 A 的成因与对策。
