1核心：Redis 是一台数据结构服务器

中文英文 / 命令含义与注意点课程
数据结构服务器 data structure server Redis 官方对自身的定义，原话："Redis is a data structure server."官方含义是：它首先是个「存各种数据结构」的服务，缓存只是它的用法之一。这一条决定了你写的是键空间设计，而不只是「塞个值进去」。 1
键 / 值 key / value 值有类型（String、Hash、List…），类型由写入的命令决定，不能事后改。把一个 String 当 Hash 用会直接报 WRONGTYPE。 1
键空间 keyspace 一个实例里全部键的集合，是全局共享的命名空间（不像数据库有表来隔离）。所以键名必须自带业务前缀，否则极易和别人的键撞车。 1
键命名约定 key naming 社区通行写法 业务:实体:id[:维度]，如 order:8801:detail。冒号只是习惯、Redis 不解析它，但它能让 SCAN MATCH 的清理和权限治理成为可能。 1
哈希字段 hash field Hash 内部的一级「字段名 → 值」。一个 Hash 里的字段不能单独设过期（除非 7.4+，见下）。 1
游标 cursor（SCAN） SCAN 的迭代位置。官方只对完整迭代作保证：元素可能重复返回、单次数量不保证、游标回到 0 才算结束。官方 1

2过期与内存：最容易出事的一节

最常被混为一谈的一组词

过期（expiration）是你主动给 key 设定的到期时间。
淘汰（eviction）是Redis 在内存超限、又找不到可回收空间时，按 {maxmemory-policy} 自行踢掉 key。
两者都会让 key 消失，但成因、可控性、排查方式完全不同。把淘汰问题当成过期问题查，是最典型的排查方向性错误。

中文英文 / 命令含义与注意点课程
存活时间 TTL · time to live key 的剩余寿命。TTL 的返回值有三种语义：正数=剩余秒数、-1=key 存在但没有 TTL（永久）、-2=key 不存在。看到 -1 就说明你已经踩坑了。 1
易失键 volatile key 官方术语：带有 TTL 的 key。所有 volatile-* 淘汰策略只在这类 key 里挑牺牲品。官方 1
过期清除 clear / persist 官方原文：只有删除或整体覆盖内容的命令会清掉 TTL（DEL、SET、GETSET、所有 *STORE）；原地改值的不清（INCR、LPUSH、HSET）。官方这是第 1 课的核心考点。 1
保留 TTL KEEPTTL SET 的选项。默认 SET 会清掉原 TTL，加 KEEPTTL 才保留。 1
字段级过期 field-level TTL Redis 7.4.0 起才有：HEXPIRE / HPEXPIRE / HEXPIREAT / HTTL / HPERSIST。低版本没有，别在旧实例上写。官方 1
内存上限 maxmemory 触发淘汰的门槛，默认 0 = 不限制（64 位系统）。注意：复制 / AOF 缓冲区占的内存不计入 maxmemory，所以 real RSS 会比 maxmemory 高。官方 1
淘汰策略 maxmemory-policy 全部取值：noeviction、allkeys-lru、allkeys-lrm、allkeys-lfu、allkeys-random、volatile-lru、volatile-lrm、volatile-lfu、volatile-random、volatile-ttl。volatile-* 在没有任何带 TTL 的 key 时会退化成 noeviction（＝写请求开始报错）。 1
最近最少使用 / 最不常使用 LRU / LFU / LRM 三种淘汰启发式：LRU 看「多久没用」、LFU 看「用的次数少」、LRM（least recently modified，较新）看「多久没被修改」，适合读多写少、想保住老数据但清掉陈旧写入的场景。 1
命中 / 未命中 keyspace_hits / keyspace_misses INFO stats 里的两个计数器，命中率 = hits ÷ (hits + misses)。官方提醒：EXISTS 报「不存在」也算一次 miss。另有 evicted_keys（被淘汰数）与 expired_keys（过期数）用来区分「是淘汰掉了还是过期掉了」。 1

3缓存模式与一致性

中文英文含义与注意点课程
旁路缓存 Cache-Aside 应用自己管缓存：读先查缓存、未命中回源并写回；写则先动数据库再删除缓存（而不是更新缓存）。最常用的模式。 待排
缓存穿透 ·存疑 （无一手定义） 中文社区叫法，指查询数据库里也不存在的数据，缓存永远不命中，请求全部打到数据库。通行的应对是缓存空值或布隆过滤器。 待排
缓存击穿 ·存疑 thundering herd / stampede 中文社区叫法，对应英文的 thundering herd：某个热点 key 刚好失效，大量并发同时回源。Facebook 论文里的解法是 lease。NSDI '13 待排
缓存雪崩 ·存疑 avalanche（社区叫法） 中文社区叫法，指大量 key 同一时刻集中失效或缓存整体不可用，导致回源洪峰。应对核心是让过期时间离散。 待排
软 / 硬 TTL soft TTL / hard TTL AWS 提出的双层过期：soft TTL 之后开始异步刷新，下游不可用时先用旧值继续服务，直到 hard TTL 才真正不可用。AWS 待排
租约 lease Facebook 论文中解决「旧值被写回」（stale sets）的机制：miss 时发一个 lease-id，一旦该 key 被删除 / 失效，旧 lease 立即作废，持旧 lease 的写会被拒绝。NSDI '13 待排
热 key / 大 key hot key / big key 社区叫法，但指向的问题很实在：热 key 打满单分片，大 key 在单线程上造成长阻塞（如 DEL 一个几百万元素的 ZSet）。 待排

4分布式原语

中文英文含义与注意点课程
分布式锁 distributed lock 官方单实例范式：SET resource_name my_random_value NX PX 30000，释放时用 Lua 先比对随机值再删，防止误删别人的锁。官方 待排
红锁 Redlock 官方主张的多实例算法：N=5 个独立 master，多数派（≥3）成功且总耗时小于锁有效期才算获锁。注意官方页面未提争议。 待排
栅栏令牌 fencing token Kleppmann 的解法：锁服务发放单调递增的编号，存储端拒收编号回退的写。他明确指出 Redlock "fails to generate fencing tokens"。原文 待排
限流 rate limiting 常用实现：固定窗口（INCR + EXPIRE）、滑动窗口（ZSet）、令牌桶。三者的边界行为不同，取舍在后续课程展开。 待排

5持久化与存储

中文英文含义与注意点课程
快照持久化 RDB 按时间点把整个数据集落成文件。体积小、恢复快，但两次快照之间的数据会丢。 待排
追加日志持久化 AOF 追加写命令日志。丢失窗口由 appendfsync 决定：always（*"Very very slow, very safe"*）、everysec（默认，*"you may lose 1 second of data"*）、no（*"The faster and less safe method"*）。官方 待排
