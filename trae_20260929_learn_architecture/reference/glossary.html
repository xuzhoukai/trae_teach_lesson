参考文档 术语表 · Glossary Mission Resources

术语表

这套课程里出现的每个名词，都以下表为准。术语一旦在这里定下，后续所有课程、练习、评审都不再换说法——术语漂移是架构讨论失败的第一原因。

1架构与决策

中文英文一句话定义
软件架构Software Architecture 系统的一组结构，包含元素、元素之间的关系，以及支配其设计与演化的原则。判断标准不是「画得漂不漂亮」，而是改起来贵不贵：改一处要动很多模块的，才算架构。
架构决策Architectural Decision 影响结构、非功能特性、依赖关系、接口或构建方式的决策。它应当被写下来，因为它是后续所有小决策的上下文。Nygard 2011
架构显著需求Architecturally Significant Requirement (ASR) 真正会改变结构的需求。功能需求通常不是 ASR，质量属性需求几乎总是 ASR。
架构决策记录Architecture Decision Record (ADR) 一两页的短文档，记录一次架构决策：标题、上下文、决策、状态、后果。一个决策一个文件，编号不复用，永不删除，只标 superseded。原文
演进式设计Evolutionary Design 不追求一次设计到位，而是让设计持续可改：保持松耦合、隔离变更、让替换局部可行。

2质量属性与场景（本课程的核心词汇）

中文英文一句话定义
质量属性Quality Attribute (QA) 描述系统「做得多好」的属性，而非「做什么」。也叫非功能需求（NFR）、「ility」。质量属性之间必然互相牵制，架构的本质就是它们的取舍。
质量属性场景Quality Attribute Scenario 把一句模糊的质量要求，写成可度量、可测试的六要素句式。它是质量属性需求的规格说明，也是将来验收的测试用例。SEI
刺激源Source of Stimulus 刺激来自哪里：外部用户、内部系统、定时器、攻击者、开发人员。
刺激Stimulus 到达系统、需要被应对的那个条件或事件。
环境Environment 刺激发生时的系统状态：正常运行、峰值负载、部分故障、启动中、上线部署中。
制品Artifact 被刺激作用的那部分系统：整个系统、某个服务、数据库、接口。
响应Response 刺激到达后系统做了什么：处理、拒绝、降级、排队、返回旧数据。
响应度量Response Measure 用数字判定响应是否达标：延迟、吞吐、成功率、恢复时间、改动成本。没有它，场景就不成立。
通用场景General Scenario 与具体系统无关的场景模板，用来生成具体场景。相当于质量属性的需求检查表。SEI
效用树Utility Tree 把「系统效用」逐层拆到场景并标注优先级（重要性 / 实现难度）的树。ATAM 的第 5 步产出物。

3评审与取舍

中文英文一句话定义
架构权衡分析方法ATAM SEI 提出的架构评估方法：从业务驱动 → 场景 → 分析架构决策 → 找出风险、敏感点、权衡点。SEI
风险Risk 可能导致某个质量属性无法达成的架构决策。评审的产出不是「架构好不好」，而是风险清单。
非风险Non-Risk 被明确验证过、可以放心依赖的决策。写下来能防止团队反复怀疑同一件事。
敏感点Sensitivity Point 这个决策稍微一动，某个质量属性就明显变化。它是性能/可用性的杠杆点。
权衡点Tradeoff Point 同时影响两个以上质量属性的敏感点。所有架构的真实战场都在这里。

4分布式与容错

中文英文一句话定义
服务边界Service Boundary一个服务负责什么、不负责什么的分界线。它是设计决策，不是代码目录。
限界上下文Bounded Context领域驱动设计中的概念：某个模型定义明确生效的边界。常被用作服务拆分的依据。
最终一致性Eventual Consistency允许副本短期不一致，但保证在没有新写入后收敛到一致。
幂等Idempotency同一请求执行多次与执行一次效果相同。异步消息与重试场景下的必备属性。
熔断Circuit Breaker下游持续失败时快速失败、不再打过去，避免连锁拖垮自己。Azure
舱壁Bulkhead把资源（线程池、连接池、实例）隔离，让一个组件的故障不耗尽全局资源。
补偿事务Compensating Transaction / Saga跨服务业务用「一步步做 + 出错反向补偿」替代分布式事务，换取可用性。补偿是一次新的本地事务，不是回滚。
事务性发件箱Transactional Outbox把「改库」与「待发消息」写在同一个本地事务里，再由后台投递，从而在无分布式事务的前提下做到事件不丢、不产生幽灵事件。
编排 / 编舞Orchestration / ChoreographySaga 的两种协调方式：编舞靠各服务发布领域事件接力，分散但难看清全局；编排由协调器发号施令，集中好排查但多一个要运维的组件。
对账Reconciliation定时比对多方（订单、支付、库存）状态，捞出最终一致性下的漏网差异。是补偿失败后的最后一道兜底。
死信队列Dead Letter Queue (DLQ)反复消费失败的消息的隔离区，避免它阻塞正常消息，同时保留现场供人工处理。
金丝雀发布Canary Release先把少量流量切到新版本，用真实指标验证后再全量。是「可修改性/可靠性」的落地手段。
可观测性Observability靠日志、指标、链路追踪回答「系统现在到底在发生什么」。没有它，所有质量属性都不可验证。

5承诺与目标（谈可用性时必用）

中文英文一句话定义
服务等级协议SLA对客户的承诺，通常带赔付条款。是「对外说出去的话」。
服务等级目标SLO团队自己定的内部目标，留出比 SLA 更严的余量。是「自己盯的线」。
恢复时间目标RTO故障后多久必须恢复。决定你要不要多活、多活怎么做。
恢复点目标RPO最多能接受丢多少数据（通常以时间衡量）。决定复制策略与备份频率。

6使用约定

约定

课程与练习中一律使用本表中「中文（英文）」的写法：首次出现写全称，之后可用中文简称。如果有人（包括你自己）在讨论里用了一个不在表里的词，先把它补充进本表并给出定义，再继续讨论。

易混淆 · 先看刺激类型

判断一条场景属于哪个质量属性，先看刺激是什么：量变（请求变多）→ 性能；故障（节点崩溃、可用区不可用）→ 可用性；出错（结果不正确）→ 可靠性；变更（业务提需求）→ 可修改性；攻击（非授权访问）→ 安全。

可用性 × 可靠性：可用性答「还能不能用」，度量是可用时间比例与恢复时间（RTO）；可靠性答「结果对不对」，度量是成功率、错误率、数据是否丢失。「正常流量下错误率 < 0.1%」属于可靠性，不是可用性——因为它没有任何故障刺激。

可修改性 × 可扩展性：可修改性是「改代码/改结构的成本」，可扩展性是「加资源能不能扛住更多负载」。
