架构决策记录（ADR）：模板与规则

ADR 是你所有设计练习的最终产出物。以后每一课的练习都按本页模板写，格式一旦定下就不换。Nygard, Documenting Architecture Decisions (2011)

1模板

一个决策一个文件，Markdown 存进仓库，一到两页以内。五部分，按序写：

docs/adr/0001-<短横线标题>.md
# ADR 1：<一句名词短语标题>

## 状态
已接受（Accepted）

## 上下文
这里描述当时「存在哪些张力」：技术、业务、项目约束，
语气中立，不评判对错。上下文里必须有冲突——
没有冲突就没有决策。

## 决策
「我们将……」。主动语态、完整句子。
这是本文件唯一不可替代的部分。

## 后果
正面、负面、中性的后果全部列出。
一条 ADR 的后果，往往是下一条 ADR 的上下文。

## 质量属性
促进：可修改性↑（说明）
牺牲：一致性↓（说明）

2规则

规则说明
一个决策一个文件塞进第二个决策，就说明没想清楚边界。
编号单调递增，不复用ADR 是只追加的日志，不是可以改写的文档。
永不删除，只标 superseded被推翻的决策仍留在历史里，并注明「被 ADR N 取代」。
一到两页超过两页说明把设计文档的内容塞进来了。
主动语态「我们将把支付拆成独立服务」，不是「支付服务被拆分」。
后果必须含负面只写好处 = 藏了风险。负面后果正是权衡点的证据。
最后标注质量属性促进什么、牺牲什么，强制把「换购」说清楚。
像对未来的开发者说话读者六个月后会拿它判断「这决策还成不成立」。

3三节串位：最常见的错误

上下文、决策、后果这三节最容易写混。判据只有一句：上下文写「当时有哪些互相冲突的力」，决策写「我们做什么」，后果写「会发生什么」。方案属于决策，优点缺点属于后果，补救措施不属于任何一节。

错误写出来的样子怎么改
方案写进上下文 上下文里写「拆分后下单先调库存校验、再调支付扣款」 这是决策。上下文只留张力：「单体里用一个本地事务就能保证一致性；业务要求改支付渠道不影响订单——两者冲突」。
优缺点写进上下文 上下文里写「优点内聚性提高，缺点是网络不稳定」 优点与缺点都是后果。上下文只描述事实与冲突，语气中立、不评判。
措施当后果 后果里写「加重试、加幂等控制、保证最终一致」 后果写「会发生什么」：订单与支付状态只能最终一致、必须对账、下单多一次网络调用、跨服务定位需要链路追踪。重试与幂等是缓解措施，属于另一条 ADR。
只写好处 后果只列正面 必须包含负面与中性后果。只写好处＝销售方案，不是决策记录。
决策句没有主语 「采用拆分方案」 「我们将把支付拆成独立服务，拥有独立数据库，订单通过接口调用它」——主谓宾齐全，读者才知道到底拆了什么、怎么交互。
一条 ADR 装两个决策 同时写「怎么拆」和「拆后如何保持一致」 拆成两份文件：ADR 1 写拆分边界，ADR 2 写一致性策略。一个决策一个文件。

4什么值得写成 ADR

判断标准

只有当决策满足下面至少一条才写：

  • 它影响多个质量属性（权衡点）——拆分、选型、一致性策略几乎都是；
  • 它难以逆转——上线后想推翻很贵；
  • 它有两个以上同样合理的方案——被否掉的方案必须写下来。

命名规范、目录结构、格式化这类决定不写——它们不值得占用 ADR 的注意力。

5质量属性怎么标

标「↑」或「↓」时要给出一句话证据，否则等于没标：

  • 促进：可修改性↑——新增支付渠道只改支付服务，订单服务零改动；
  • 牺牲：一致性↓——订单与支付状态只能最终一致，需要对账兜底。
