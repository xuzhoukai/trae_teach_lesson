质量属性场景：六要素速查

撕下来贴在显示器边上。任何一次「系统要快 / 要稳 / 要好维护」的讨论，都先用这张卡把它变成一句能验收的话。

1句式模板

模板

当 【刺激源】 在 【环境】 下对 【制品】 发起 【刺激】 时，系统应 【响应】，且 【响应度量】。

  • 刺激源Source of Stimulus谁引发的：外部用户、内部系统、定时器、攻击者、开发/运维人员。
  • 刺激Stimulus发生了什么：一次请求、一批并发流量、一个节点宕机、一个变更需求。
  • 环境Environment当时系统处于什么状态：正常、峰值、部分故障、上线中、维护窗口。
  • 制品Artifact受影响的是谁：整个系统、下单服务、订单库、对外 API。
  • 响应Response系统做了什么：正常处理、排队、降级、返回旧值、拒绝、自动切换。
  • 响应度量Response Measure用什么数字判定达标：P99 延迟、成功率、恢复时间、改动人天。

2合格场景的三个判据

判据不合格的样子合格的样子
可度量
有数字和单位		 「下单要快」 「P99 下单响应时间 ≤ 300 ms」
有环境
说明当时状态		 「任何时候都要快」 「在大促峰值（5000 TPS）下」
可测试
能被观测或压测验证		 「系统要稳定」 「单可用区故障时，30 秒内自动切换，成功率达 99.9%」

判据来源：SEI, Reasoning About Software Quality Attributes；评估流程见 ATAM Collection。

3常见质量属性的通用场景（起手模板）

这些是与具体系统无关的模板，用来生成你自己的具体场景。取用时必须把方括号替换成真实数字与真实组件，否则等于没写。

先看刺激

判断属性归属，先问「刺激是什么」：量变 → 性能，故障 → 可用性，出错 → 可靠性，变更 → 可修改性，攻击 → 安全。填不出刺激的那一格，正是需求还没想清楚的地方——去问，不要编。

质量属性刺激典型响应典型度量
性能
Performance		 周期性或零星到达的事件、请求 处理事件；在负载超限时排队或拒绝 延迟（P99）、吞吐（TPS/QPS）、抖动、超时比例
可用性
Availability		 节点崩溃、进程挂死、外部依赖超时 检测故障 → 记录 → 通知 → 切换到备用 → 继续服务 可用时间比例（如 99.95%）、故障恢复时间、故障间隔
可修改性
Modifiability		 需求变更、平台/依赖升级、环境变化 完成修改、构建、测试并部署，且不影响其他功能 改动工作量（人天）、影响的服务数、发布所需时间
安全
Security		 对数据或服务的非授权访问、篡改、拒绝服务尝试 识别 → 拒绝 → 记录 → 通知；保证合法用户可用 检测所需时间、被拦下的比例、对正常请求的影响
可测试性
Testability		 测试人员/自动化流水线发起验证 提供可观测状态与隔离环境，暴露失败原因 回归所需时间、用例覆盖率、故障定位时间

改编自 SEI 通用场景（general scenarios）、ISO/IEC 25010:2023 的质量特性清单。ISO 25010 2023 版已把 Usability 改为 Interaction capability、Portability 改为 Flexibility，并新增 Safety——引用标准时注意版本。

可用性要按链路算

端到端可用性是依赖的乘积：把 4 个各 99.9% 的服务串在一条同步链路上，链路成功率约 99.6%（0.999⁴ ≈ 0.996）——四个九掉成三个九。每增加一个同步强依赖，都要重算一遍可用性场景。

这也是拆分对可用性的真实账：故障被隔离了（↑），但依赖变多了（↓）。所以标注方向时必须落到具体链路上，不能整体写一个箭头。

4常见错误（评审时照着挑）

错误例子怎么改
没有度量「保证高可用」补上「单可用区故障时 30 秒内切换，成功率 ≥ 99.9%」
没有环境「响应时间 1 秒内」补上「在峰值 5000 TPS、缓存命中率 90% 时」
把实现当需求「必须用 Kafka 做异步解耦」改写成目的：「订单创建后 2 秒内完成通知投递，允许最终一致」
一个场景混两个质量属性「既要快又要能自动扩容还要安全」按质量属性拆成三条场景，各自给度量
度量不可观测「代码要优雅」换成可测的形式：「新增一个支付渠道，改动不超过 2 个服务、5 人天」
只写理想路径只描述流量正常时必须包含「部分故障 / 超载 / 依赖超时」等环境

5三个可直接抄的成品（仿真需求：电商订单系统）

性能

当外部用户在峰值负载（5000 TPS、在线 20 万）下对订单查询接口发起查询请求时，系统应在200 ms 内返回结果，且P99 延迟 ≤ 200 ms、错误率 ≤ 0.1%。

可用性

当单个可用区在业务高峰期间发生故障时，下单链路应在30 秒内自动切换到其他可用区继续接受下单，且成功率 ≥ 99.9%、不丢失已支付订单。

可修改性

当业务方在系统已上线运行时提出新增一种支付渠道的需求，支付服务应能在不改动订单服务代码的前提下完成接入，且改动范围 ≤ 1 个服务、≤ 5 人天、不影响既有渠道。

6下一步

  • 写完之后，问自己三句话：这个数字怎么测？谁测？测不达标时改什么？——最后一问答不上来，说明还没有对应的架构决策。
  • 把场景当测试用例用：每个场景都应能关联到一条压测、一次故障演练或一份验收清单。
