第 6 课 约 30 分钟 Mission 术语表 ADR 模板

数据存储与一致性：你卖的到底是哪一级「一致」

前五课里，「一致性」已经出现过三次：拆分时失去本地事务、Saga 的最终一致、S5 的「明确结果」。这一课把它拆开：事务一致性、复制一致性、业务一致性是三件不同的事，用错药会治错病。

⚡ 补正 · 5 分钟（第 5 课遗留）

内部状态不等于用户可见结果。第 5 课你把 S2 的「不达标」写成「支付失败，订单是待支付状态」。这里有两次错位：待支付属于达标（请求已受理），而且「订单表里是什么状态」和「用户在页面上看到什么」是两件事。

本课会反复用到这条：数据库写入成功，不代表用户下一次读能看到。比如订单库里已是 PAID，但详情页走的是只读副本，复制延迟 300ms，用户点进去看到的仍是 PENDING——指标全绿，用户却在投诉。所谓「一致」，必须先回答：谁在读、读的是哪一份数据、允许落后多久。

1三种「一致性」，先分开

层级谁保证什么时候失效典型症状
事务一致性
（ACID）		 单个数据库的本地事务 数据被拆到多个库、或跨服务写入时 扣了库存没建订单；一个事务只成功了一半
复制一致性
（主从 / 多副本）		 数据库的复制机制 异步复制有延迟；备库落后于主库 刚下单查不到订单；刷新两次看到的状态来回跳
业务一致性
（跨服务最终一致）		 Saga、发件箱、对账（ADR 2） 补偿失败、消息丢失、对账周期之间 订单已支付、库存没扣；通知迟迟不发
关键结论

说「我们要强一致」之前，先回答：是要求单库事务原子（第一层）、要求读到自己刚写的数据（第二层）、还是要求两个服务的状态最终对齐（第三层）？三者的成本差一个数量级：单库事务几乎免费，跨服务强一致基本不可能，通常只能用最终一致加对账。

2复制：同步还是异步，是在选 RPO

以 PostgreSQL 为例，synchronous_commit 决定「服务端在向客户端返回成功之前，WAL 要处理到什么程度」，取值有 remote_apply、on（默认）、remote_write、local、off。PostgreSQL Docs

模式提交成功意味着什么代价
off / local只保证本地写入，主库宕机可能丢最近的事务最快，但 RPO > 0
on（同步）备库已把 WAL 落盘；主库崩溃不丢已提交事务提交延迟被备库绑定，备库慢则写入慢
remote_apply备库不仅收到、还**已应用**，备库查询能读到最新延迟最高，跨地域时尤其明显

注意最后一行的差别：很多人以为「同步复制」就等于「从库能读到最新」，其实 on 只保证落盘，备库的查询一致性要 remote_apply 才有。这就是为什么「写主读从」会出现读不到自己刚写的数据。

文档还特别指出：这个参数可以按事务设置——默认同步，个别非关键事务用 SET LOCAL synchronous_commit TO OFF 异步提交。这正是架构上该做的事：按数据类型分级，支付与订单同步，日志与埋点异步。

3「写主读从」的经典事故：读不到自己刚写的

场景你一定见过：用户下单成功，页面跳到订单详情，显示「订单不存在」；用户再刷新一次，又出来了。这不是下单失败，而是写主读从的复制延迟。

这类一致性有两个必须分开的要求：

  • 读己之写（Read Your Writes）：用户自己刚写的数据，自己下一次必须能读到。
  • 单调读（Monotonic Reads）：用户这次读到了新状态，下次不能退回旧状态（否则页面看起来「倒带」）。

四种可选解法，代价不同：

解法做法代价
关键路径读主「下单后跳详情」这类请求强制走主库主库读压力上升；要维护一张「哪些请求可读从」的清单
会话粘滞同一用户的读写都路由到同一副本负载不均；故障切换时仍会短暂读到旧数据
按位点等待写操作返回 LSN/版本号，读时带上，等待副本追到该位点读延迟增加；需要客户端配合传版本号
客户端本地缓存写入结果直接缓存在客户端，详情页先用它只覆盖刚写完的那一小段时间，刷新或换设备就失效

没有「都读主」这种解法——那等于放弃读写分离。你要选的是哪几条读路径必须读到最新，其余接受延迟。

4缓存：三个 Amazon 踩过的坑

AWS 那篇缓存文章的标题很直白：缓存的狂喜与痛苦。它讲了一个典型过程：加缓存后延迟下降、成本降低、下游抖动也被抹平；于是团队缩小了下游的机器规模、把数据库降配；直到某天缓存集群故障或流量模式突变，请求全部涌向下游，把自己的依赖和自己一起打挂。AWS

三个必须记住的结论：

  1. 缓存会引入「模态行为」：命中缓存和未命中是两套行为，流量在两者间的分布一旦突变，就可能引发灾难。缓存不是「无脑加速」，它改变了系统的失败模式。
  2. 缓存集群挂了，不要自动回退直连数据库。AWS 明确说这会在长时间故障中造成异常流量尖峰，把下游打到限流甚至降级；他们更倾向「内存缓存兜底」或「负载卸载 + 限制发往下游的最大速率」。AWS
  3. 用两个 TTL：软 TTL 到期就尝试刷新，但下游不可用时继续用旧值，直到硬 TTL。AWS

另外，本地（进程内）缓存有两个特有麻烦：各机器数据不一致（同一用户两次请求打到不同机器，看到新旧不同的值）和冷启动（发布后所有实例缓存全空，瞬间把下游打满）。外部缓存解决了这两点，但又带来「多一个可能不可用的组件」。AWS

判据

能不能上缓存，先问两个问题：① 这份数据变更多快、能容忍多旧？② 缓存全挂时，下游扛不扛得住回源流量？第二个问题答不上来，就不该上——那不是缓存，是给自己埋了一颗定时炸弹。

5分库分表：最后才动的手术

分片不是「数据大了就该分」。先按顺序排除更便宜的方案：

  1. 索引与慢查询治理——大部分「数据库扛不住」其实是查询写法问题；
  2. 读写分离——把查询压力挪走（但要处理上一节的读己之写）；
  3. 归档与冷热分离——三年前的订单不该和今天的订单抢同一张表；
  4. 垂直拆分——把大字段（详情、日志）挪到独立表；
  5. 水平分片——最后才做。

真要分片，第一件事是选分片键，它决定你以后能做哪些查询：

  • 按 order_id 分：订单详情天然单分片，但「查某用户的所有订单」变成跨分片广播；
  • 按 user_id 分：用户维度查询快，但按订单号查要先知道用户；
  • 按时间分：范围查询友好，但热点集中在当前分片。
注意：分区 ≠ 分片

如果 C 端查询天然带时间边界（例如产品规定只能查最近 3 个月），按月分区是另一种更简单的方案：每个分区只放一个月的数据，查询自动裁剪到 1–3 个分区，归档就是 DROP PARTITION，扩容就是加一个分区，且不需要分布式中间件。判据只有一条：查询是否永远带时间条件。带，就按月分区；不带（要查全部历史），才考虑按用户维度分片。

分片的代价是永久性的：跨分片事务没了、跨分片分页/聚合要自己写、全局唯一 ID 要另设方案、扩容 rehash 需要迁移数据。所以第 5 步的位置不能提前——分片键一旦定下，改它的成本接近重做系统。

另外，服务拆分之后还有一条硬规矩：每个服务只通过自己的库访问数据，其他服务不许直连你的库；跨服务的查询靠 API 组合或 CQRS 物化视图，而不是「连过去 join 一下」。microservices.io

6选型：按「读什么、能旧多久」定

场景方案主要代价
订单详情（用户刚下单就看）写主读主，或按位点等待主库读压力
订单列表（可容忍秒级延迟）读写分离 + 只读副本复制延迟、偶发旧数据
商品详情（读多写少、容忍分钟级旧）外部缓存 + 软/硬 TTL缓存一致性、缓存故障时的回源风险
库存扣减（不能超卖）单库事务 / 行锁，不分片或按 SKU 分片热点 SKU 成为瓶颈
历史订单查询（低频、量大）归档库 / 冷热分离跨库查询、运维成本
跨服务联合查询API 组合或 CQRS 物化视图额外调用或最终一致

动手练习 · 约 25 分钟

给订单库定存储方案，并写 ADR 5

上下文（延续前五课）

订单服务已有 ADR 1–4。当前订单库是单实例 PostgreSQL，主从异步复制，未分片。

业务给出的数字：订单表 3 年约 6 亿行；峰值下单写入 800 TPS；峰值订单查询 5000 TPS（S1 要求 P99 ≤ 200ms）；单条订单详情约 2KB；历史订单查询占比约 30%。

用户路径：下单成功 → 跳转订单详情；用户也可能在「我的订单」列表里翻最近 3 个月的订单。

任务（四步，按序做）：

  1. 先排除便宜方案：按本课第 5 节的顺序，逐条说明「索引治理 / 读写分离 / 归档冷热分离 / 垂直拆分」分别能不能解决，哪一条必须先做。
  2. 决定是否分片：给出你的判断（分或不分），若分，写清分片键、分片数，以及「按订单号查」和「按用户查列表」这两条查询各自会变成什么代价。
  3. 读一致性方案：分别给「下单后跳详情」和「我的订单列表」两条读路径定方案，说明能容忍多旧的数据（秒？分钟？），以及为什么。
  4. 写 ADR 5（题目：订单库的存储与读一致性策略）：五部分齐全，后果必须含负面项（跨分片查询、扩容迁移、主库读压力、缓存回源风险等）。
自检清单（写完逐条勾）
  • 有没有把「分片」当成第一反应？分片之前那四步是否逐条排除过？
  • 分片键选的是**业务键**吗？它让哪类查询变便宜、哪类变贵，写清了吗？
  • 「下单后跳详情」有没有明确走主库或按位点等待？还是默认读从？
  • 缓存方案有没有回答「缓存全挂时下游扛不扛得住回源」？
  • ADR 后果里有没有写：跨分片查询代价、扩容迁移成本、主库读压力、缓存一致性窗口？
  • 有没有把「加索引」「加缓存」这类**措施**写进后果？它们属于决策。
参考思路（先自己写完再看）

① 排除便宜方案——索引治理先做：订单查询若缺 (user_id, created_at) 复合索引，5000 TPS 会直接打满 I/O；读写分离可承接大部分列表查询，但必须解决读己之写；归档冷热分离把 3 个月前订单移出主表，直接砍掉 70% 的查询面；垂直拆分把详情大字段移走，降低单行宽度与缓存压力。结论：先做索引 + 归档 + 垂直拆分，再谈分片。

② 是否分片——6 亿行、单行 2KB，主表约 1.2TB。先做索引治理与垂直拆分，再用归档把在线表压到 1 亿行以内。若产品规定 C 端只能查最近 3 个月（本课练习的隐含前提之一），首选 PostgreSQL 按月原生分区：单分区约 33GB，查询自动裁剪到 3 个分区，归档即 DROP PARTITION，扩容即加分区，且不需要分布式中间件。代价是「按订单号查」必须能定位分区（订单号编码月份），以及分区表的主键要写成 (order_id, created_at)。只有当查询不再带时间边界、需要跨用户查全部历史时，才改为按 user_id 分片。

③ 读一致性——「下单后跳详情」：读主库（或带写入 LSN 等待副本追平），可容忍延迟 = 0；理由：这是用户刚完成动作后的确认页，读到旧数据会被理解成下单失败，直接引发重复下单。「我的订单列表」：读只读副本，可容忍延迟 = 数秒；理由：列表本来就按时间倒序，少一条刚下的订单不会造成误判，且能省下主库大量读压力。缓存只用于商品详情这类读多写少数据，订单状态不进缓存（变更频繁且要求即时可见）。

④ ADR 5 摘要——上下文：在线表 6 亿行、峰值查询 5000 TPS、P99 ≤ 200ms；主从异步复制，副本落后时用户可能读不到刚下的订单；历史查询占 30%；C 端仅可查询最近 3 个月，这是方案成立的前提。决策：我们先做索引治理与垂直拆分，再按月做 PostgreSQL 原生分区（分区键为下单时间），订单号中编码月份用于定位分区；「下单后详情」强制读主，列表读只读副本；订单状态不缓存；旧分区 detach 后迁冷库。后果——正面：查询裁剪到 3 个分区、P99 可控、归档与扩容都极简；负面：不带时间条件的查询会退化为扫全部分区（靠订单号编码月份兜底）；跨月分页需归并、深分页成本高；每月需自动建分区，漏建会导致写入失败；分区键固定为下单时间，「按支付时间」类查询要另建读模型；方案与「3 个月可见」强绑定，产品规则一放开就要重做存储架构。质量属性——性能↑（S1 达标）、可用性↑（副本分担读压力）、一致性↓（列表存在秒级陈旧窗口）、可维护性↓（分区运维 + 产品约束耦合）。
