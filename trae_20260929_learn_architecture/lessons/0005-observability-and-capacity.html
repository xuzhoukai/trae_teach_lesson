第 5 课 约 25 分钟 Mission 术语表 ADR 模板

可观测性与容量：没有仪表盘，质量属性只是口号

前四课你已经能写出 S1–S5、拆了服务、定了最终一致与容错参数。这一课补上最后一环：怎么证明这些目标在线上真的达成了，以及容量该按什么数字扩。

⚡ 补正 · 5 分钟（第 4 课遗留）

① 判据要改成「结果未知」而不是「执行了」。第 4 课你把「连上了不回应」判成「执行了 → 不能重试」。正确写法是：

失败时你知道什么能不能重试
确定没执行（连接被拒、参数校验失败）可以，无副作用
确定执行失败且不会成功（业务规则不满足）不可以，重试也一样
不知道有没有执行（读超时、响应丢失）有幂等键才可以

这张表在本课还有第二个用途：错误码必须能区分这三类。分不清「未知」和「失败」，就没法自动重试，也没法告警——这正是可观测性要解决的第一件事。

② 未知就说未知。第 4 课你把「库存服务不可用」写成「返回无货」。库存服务挂了，系统并不知道有没有货。对外文案与错误码都要区分「业务事实」（确实无货）与「系统未知」（暂时无法确认）——否则你的监控会统计出一个假的「缺货率」。

1先修词：SLI 与 SLO

两个词的定义以 OpenTelemetry 的观测入门文档为准：SLI（Service Level Indicator）是对服务行为的测量，好的 SLI 从用户视角定义服务（例如网页加载多快）；SLO（Service Level Objective）是把 SLI 绑到业务价值上，用来向组织沟通可靠性。OpenTelemetry

把它套到你的场景上：

场景SLI（怎么测）SLO（目标）不合格的替代品
S1 性能 订单查询请求的服务端延迟分布 P99 ≤ 200ms CPU 利用率 < 70%
S2 可用性 下单请求成功返回的比例 ≥ 99.9% 进程存活（心跳绿）
S5 容错 1 秒内得到明确结果（成功/失败/处理中）的请求比例 ≥ 99.9% 平均响应时间
关键结论

「进程活着」不是可用性，「CPU 不满」不是性能。SLI 必须站在用户那一侧：用户关心的是「我这次请求成没成、多快」，不是你的机器忙不忙。机器指标是排查用的原因，不是验收用的结果。

2三支柱：metrics、logs、traces

OpenTelemetry 把可观测性的信号归为三类：metrics（一段时间内的数值聚合）、logs（带时间戳的消息）、traces（一个请求穿过多个服务的路径）。OpenTelemetry

三者的分工不是并列的，而是从粗到细：

  • metrics 回答「有没有问题」：下单成功率掉了。便宜、可长期存储、适合告警。
  • traces 回答「问题在哪一段」：一个 trace 由多个 span 组成，根 span 代表整次请求，子 span 代表每一段工作（网关、订单、库存、支付、数据库）。OpenTelemetry
  • logs 回答「具体发生了什么」：某个 span 上的错误详情。文档特别提醒：日志本身缺少上下文（不知道从哪调用），只有挂到 span/trace 上、与 trace 关联后才真正有用。OpenTelemetry

所以「上了日志系统」不等于可观测。判断标准很硬：拿到一个用户投诉的订单号，你能不能在 5 分钟内定位到是哪个服务、哪一步慢了或失败了？能，才算有了追踪能力。ADR 2 里那句「订单卡在哪一步无法回答」，就是缺这条链路。

3吞吐（throughput）不等于有效吞吐（goodput）

这是本课最重要的一个反直觉结论，来自 AWS 关于过载与负载卸载的文章：throughput 是每秒发给服务的请求总量；goodput 是其中「成功处理、且延迟低到客户端还用得上」的那部分。AWS

文章描述的过载过程是这样的：

  1. 负载升高，延迟上升（线程争用、GC、I/O 争用加剧）；
  2. 延迟一旦超过客户端超时，请求开始失败 —— 延迟问题就地变成可用性问题；
  3. 超时意味着服务端已经做的工作全部白费，而客户端还会重试，把负载再放大一层；
  4. 于是过载形成正反馈，自己维持自己。AWS

AWS 的应对是负载卸载（load shedding）：接近过载时主动拒绝超额请求，把资源留给被接纳的请求，让它们仍能在客户端超时前返回。AWS

两个会骗人的指标

① 平均延迟。过载时大量请求被快速拒绝，这些「很快失败」的请求会把平均/中位延迟拉低，让系统看起来很快。AWS 明确说：不要把失败请求的延迟混进服务的延迟指标。AWS

② 被拒流量不算坏。负载卸载会故意拒绝一部分请求，所以「拒绝率上升」可能是保护机制在正常工作；你要看的是被接纳请求的 goodput 有没有守住，以及误拒率（本有容量却被拒）是否为零。

4容量：按 goodput 算，并留一个可用区的余量

容量规划常见错误是「按 CPU 到 70% 就该扩」。但 AWS 指出，服务在接近过载时会先出现延迟拐点，CPU 还没满，goodput 已经掉了；反过来，若同时配了负载卸载和基于 CPU 的自动扩缩，负载卸载把 CPU 压住，自动扩缩反而收不到扩容信号。AWS

可用的算法只有三步：

  1. 压测得到单实例的 goodput（在目标 P99 下每秒能成功处理多少），不是理论 QPS。
  2. 用峰值 goodput 需求除以单实例 goodput，向上取整。
  3. 再按「一个可用区挂掉仍能承载全量」放大。AWS 的做法正是：把服务扩到「一个 AZ 的容量失效后仍能守住延迟目标」的程度。AWS

举个可验算的例子：峰值 5000 TPS，单实例在 P99 200ms 下 goodput 为 800 TPS，三个可用区。

基本需求：5000 ÷ 800 = 6.25 → 7 台
AZ 余量：任一 AZ 故障后仍要能扛 7 台的量，即 N × (2/3) ≥ 7
        N ≥ 10.5 → 11 台（分布 4 / 4 / 3）

验算：挂掉 4 台的那个 AZ，剩 7 台恰好承载 7 × 800 = 5600 TPS ≥ 5000。这就是「容量是一个算式，不是一个感觉」。

5告警：报症状，别报原因

Azure 的监控指南把监控数据按用途分成几类：健康、可用性、性能、SLA 等，并强调要能把失败与具体活动关联起来、按分位（P99/P95）而不是只看平均来设定目标。Azure

落到告警上，有三条规则：

规则说明反例
按 SLI 告警，不按机器指标告警 「下单成功率 < 99.9% 持续 5 分钟」会响，说明用户真的受影响。 「CPU > 80%」响了但用户毫无感觉，久而久之没人看。
分级：page / ticket / log page 只给「用户已受影响且需立刻处理」；趋势问题进 ticket；其余只记录。 所有告警都打电话，等于没有告警。
每条告警有 owner 和第一步动作 告警文案里直接写「先查支付渠道回调延迟看板」。 「Something is wrong」——收到的人只能先翻文档。

另外要盯误报：AWS 把「本有容量却被拒绝」称为 false positive，并要求把误报率控制到零——长期存在误报，说明保护参数调得太敏感，或者主机真的长期过载。AWS

动手练习 · 约 20 分钟

把 S1 / S2 / S5 变成可验收的观测与容量方案

上下文（延续前四课）

系统已有 ADR 1（四服务拆分）、ADR 2（编排式 Saga，支付受理同步、扣款结果异步，`WAITING_PAYMENT` 保留库存 ≤15 分钟）、ADR 3（超时 150ms × 2 次、熔断、舱壁）。

场景：S1 峰值 5000 TPS 查询，P99 ≤ 200ms；S2 单可用区故障 30 秒内切换、下单成功率 ≥ 99.9%；S5 库存或支付不可用时 1 秒内给明确结果。

容量假设：单实例在 P99 200ms 下 goodput = 800 TPS；三个可用区。

任务（四步，按序做）：

  1. SLI / SLO 表：为 S1、S2、S5 各写一行 —— SLI 定义｜SLO 阈值｜数据来源（哪个服务的哪个指标/span）｜不达标时用户看到什么。
  2. 两条告警：一条 page、一条 ticket，各写 触发条件｜级别｜owner｜第一步动作（runbook 首句）。要求两者都不以 CPU 为主指标。
  3. 容量算式：用上面的假设算出基本台数与 AZ 余量后的总台数，写出每一步算式；并说明「为什么不能用 CPU 利用率来定扩容」。
  4. 写 ADR 4（题目：可观测性与容量基线）：五部分齐全，后果必须含负面项（例如指标存储成本、告警误报、追踪采样带来的盲区）。
自检清单（写完逐条勾）
  • 每个 SLI 都是用户视角吗？有没有混进 CPU、内存这类原因指标？
  • S5 的 SLI 有没有把「处理中」算作合格结果？（否则成功率会被异步支付永久拉低）
  • 延迟用分位而不是平均值吗？有没有说明失败请求的延迟不计入成功延迟？
  • 告警条件是「用户已受影响」还是「机器有点忙」？每条都有 owner 和第一步动作吗？
  • 容量是按goodput算的吗？AZ 余量是「挂一个 AZ 仍扛全量」，不是「随便留 20%」吧？
  • ADR 4 的负面后果里，有没有写采样率带来的盲区与指标存储成本？
参考思路（先自己写完再看）

① SLI / SLO 表——S1：SLI=订单查询请求服务端延迟的 P99；SLO ≤ 200ms；来源=订单服务查询接口的直方图指标（按路由与状态码切分）；不达标时用户看到页面转圈、超时。S2：SLI=下单请求返回 2xx 且订单状态非失败的比例；SLO ≥ 99.9%；来源=订单服务入口指标 + 订单终态统计（两者要能对账，防止「返回成功但实际失败」）；不达标时用户看到下单失败。S5：SLI=1 秒内得到明确结果（成功 / 明确失败 / 已受理处理中）的请求比例；SLO ≥ 99.9%；来源=下单入口的耗时直方图 + 三类结果计数；不达标时用户看到页面长时间无响应。

② 告警——page：「下单成功率（5 分钟滑动窗口）< 99.9%，且请求数 ≥ 100」，owner=订单服务 on-call，第一步=先看支付受理失败率与库存超时率，确认是否为依赖故障。ticket：「`WAITING_PAYMENT` 订单占比连续 1 小时 > 2%」，owner=支付服务团队，第一步=查各渠道回调延迟与查单失败率。

③ 容量——基本需求 5000 ÷ 800 = 6.25 → 7 台。AZ 余量：要求任一 AZ 故障后仍承载 7 台，即 N × 2/3 ≥ 7 → N ≥ 10.5 → 11 台，分布 4/4/3；挂掉 4 台的 AZ 后剩 7 台 = 5600 TPS，满足。不能用 CPU 定扩容，因为过载前 goodput 已开始下降而 CPU 未满；且负载卸载会把 CPU 压住，自动扩缩收不到信号（AWS 明确记录了这个副作用）。

④ ADR 4 摘要——上下文：S1/S2/S5 已是可验收的场景，但当前只有进程存活与 CPU 指标，无法回答「用户是否拿到结果」；ADR 2 的 Saga 中间态与 ADR 3 的熔断/限流会制造「计划内」的失败，若不区分会把保护机制误判为故障；追踪数据量与指标基数带来成本。决策：我们采用 OpenTelemetry 统一采集 metrics/logs/traces，所有跨服务调用透传 trace 上下文；以下单链路三条 SLI（查询 P99、下单成功率、1 秒内明确结果率）作为验收口径；告警按 SLI 分级（page/ticket），不以 CPU 为主指标；容量按压测 goodput + 峰值 + 一个 AZ 余量核算。后果——正面：质量属性可验收、跨服务排障有路径、扩容有算式；负面：指标基数与追踪存储带来成本，采样会丢掉部分异常请求的细节，告警阈值需要持续调优否则误报，SLI 口径变更会中断历史对比。质量属性——可观测性↑（直接支撑 S1/S2/S5 验收）；可用性↑（故障定位更快）；成本↓（存储与采样开销）。
