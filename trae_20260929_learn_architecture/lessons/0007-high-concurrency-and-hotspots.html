第 7 课 约 30 分钟 Mission 术语表 ADR 模板

高并发读写与热点：加机器解决不了的那部分

前六课解决的是「怎么拆、怎么一致、怎么活、怎么观测、数据放哪」。这一课面对最硬的一类问题：流量集中到一个点上，横向扩容失效。

⚡ 补正 · 5 分钟（第 6 课遗留）

「加了某个机制」不等于「问题解决了」。第 6 课你把「水平分离」写成「无一致性问题」，就是只看到了机制，没算代价。这一课把这种写法纠正为一个固定句式：

只写机制（不合格）补上三个数（合格）
加缓存缓存能扛多少 QPS？命中率多少？缓存挂了回源流量是多少？
加重试重试几次？最坏放大多少倍（5 层 × 3 次 = 243 倍）？下游扛得住吗？
加机器瓶颈是单点还是整体？如果是同一行/同一个 key，加机器有用吗？

本课所有方案都要按这个句式回答：上限是多少、超了会怎样、代价是什么。

1先算并发，再谈扩容

最常见的误判是把 QPS 当成并发。实际上：

并发数 ≈ QPS × 单请求耗时

用你的场景算一遍：

场景QPS单请求耗时并发
订单查询（正常）50002ms10
订单查询（P99 恶化）5000200ms1000
下单（含两次远程调用）800700ms560

这就是为什么「QPS 没变，服务却挂了」：耗时一涨，并发就涨，连接池和线程池先被占满。所以容量规划里必须同时约束两件事——QPS 上限与并发上限，而不是只看 QPS。

饱和点不是线性外推

服务在接近满载时延迟会急剧恶化：线程争用、GC、I/O 争用同时放大，曲线出现过载拐点；一旦延迟超过客户端超时，请求开始失败，延迟问题就地变成可用性问题，重试再把负载放大一层。AWS 所以「再撑一撑」通常是反效果。

2热点：加机器为什么没用

横向扩容的前提是请求能被分散。热点打破了这个前提：所有请求都指向同一个 key、同一行数据、同一个分片。

热点类型典型场景为什么加机器无效
热 key爆款商品详情、秒杀 SKU同一个 key 只存在一份缓存，加节点不会多出一份
热行库存扣减、账户余额同一行的更新被行锁串行化，吞吐上限 = 单行处理速度
热分片按月分区时的「当前月」、大商户数据落在同一个物理分区，机器再多也只打一处
热接口秒杀下单、整点抢券入口 QPS 远超后端任何单点的处理能力

判断方法很直接：算一算单个点的处理上限 × 1 是否 ≥ 峰值 QPS。小于，就必须拆分或限流，扩容无用。

3四类热点的拆法

热点拆法代价
热 key（读） 本地缓存 → 多副本 key（`key#0..N` 随机读）→ 请求合并（同一 key 并发只回源一次） 多副本之间可能不一致；本地缓存有冷启动与脑裂
热行（写） 乐观锁重试 / 分段库存 / 队列串行化 / 原子扣减 复杂度上升，可能牺牲「总量准确」或用户体验
热分片 二级拆分（先按 hash 再按时间）、大客户独立分片 运维复杂；跨分片聚合变多
热接口 入口限流、排队、验证码/预约、异步受理 体验下降；拒绝一部分用户是设计目标，不是 bug

4库存扣减：四种并发控制怎么选

这是本课最值得动手算的一题。同一个 SKU 只有一行库存，所有下单都要改它。

方案一：悲观锁

BEGIN;
SELECT stock FROM inventory WHERE sku = ? FOR UPDATE;
-- 应用判断 stock >= n，再执行 UPDATE
COMMIT;

FOR UPDATE 会对取到的行加行级排他锁，直到事务结束；期间其他 UPDATE、DELETE、SELECT FOR UPDATE 在同一行上都要等。PostgreSQL Docs

上限：吞吐 ≈ 1 ÷ 持锁时长（单行）。持锁 5ms → 200 TPS。风险：长事务会把整条链路堵死。

方案二：乐观锁

UPDATE inventory SET stock = stock - ?, version = version + 1
WHERE sku = ? AND version = ? AND stock >= ?;

影响行数为 0 就表示冲突，重试。上限：冲突率低时接近无锁；风险：秒杀场景冲突率接近 100%，重试风暴反而把负载放大数倍。

方案三：原子扣减（最常用）

UPDATE inventory SET stock = stock - ?
WHERE sku = ? AND stock >= ?;

一条语句完成「判断 + 扣减」，天然不会超卖；但它在行上仍要拿锁，并发本质仍是串行。上限同样是单行处理速度，只是省掉了一次往返与长事务。

方案四：分段库存

把 1000 件拆成 10 段各 100 件，请求按 hash 落到某一段，把「单行锁」变成「10 行锁」，吞吐约提升 10 倍。

代价：可能出现「某段售罄但总库存还有」，用户看到有货却下单失败；需要用「跨段借调」或「剩余量聚合展示」来兜。这是典型的用准确性换吞吐。

方案五：队列串行化 / Redis 预扣

把同一 SKU 的请求投进队列，单消费者串行处理——没有并发冲突，但吞吐上限 = 单线程处理速度。Redis 预扣把判断放到内存，吞吐高，但要面对「Redis 与数据库不一致」「Redis 宕机丢预扣」的对账问题。

方案单 SKU 吞吐超卖风险主要代价适用
悲观锁低（数百 TPS）无长事务阻塞低冲突、强一致
乐观锁低冲突时高无高冲突时重试风暴冲突率低
原子扣减中（单行上限）无仍是串行普通商品
分段库存高（约 N 倍）无（但会「假售罄」）跨段调度、体验秒杀
队列串行 / Redis 预扣取决于单消费者/内存需对账兜底一致性、复杂度秒杀 + 异步下单

5限流与排队：队列不是垃圾桶

AWS 对队列的描述值得整段记住：队列系统有两种模式。没有积压时延迟很低（快模式）；一旦到达速率超过处理速率，就会迅速切换到另一种模式——端到端延迟不断升高，而且要花很长时间才能把积压消化完、回到快模式。AWS

两个具体的数：

  • 经历一小时的处理中断后，恢复需要以双倍处理能力再跑一小时；如果下游也扛不住这波追赶流量，恢复会更久。AWS
  • 积压达到消费能力的 10 倍时，即使 30 分钟后开始处理，也要 300 分钟才能消化完 —— 一次短促的流量尖峰，可以变成数小时的故障。AWS

由此得到四条工程规则：

  1. 队列必须有界，满了就拒绝，不能让积压无限增长；
  2. 拒绝要趁早：在入口就拒，比收进来再超时便宜得多（后者还浪费了已经完成的工作）；
  3. 双倍容量追赶是硬需求：故障恢复期要预留额外处理能力，否则永远追不上；
  4. 只盯 DLQ 太晚：消息进死信队列时，用户早就受影响了。要看「消息在队列里的年龄」（first-attempt age），而不是只看失败率。AWS

多租户场景还要加一条：按租户限流（公平性）。AWS 的做法是按客户设置速率上限并允许一定突发，避免一个客户的尖峰演变成全系统的积压。AWS

动手练习 · 约 25 分钟

设计一场秒杀：热点识别、库存方案、拒绝策略

上下文（延续前六课）

单品库存 1000 件；活动开始瞬间 10 万人同时点击，入口峰值 5 万 QPS；预期 1 秒内售罄。要求：不超卖、系统不宕机，允许一部分用户明确失败。

现有约束：订单库按月分区（ADR 5）；库存是数据库中的一行；下单链路含库存扣减与支付受理（ADR 2/3）。

已知量：单行库存更新的处理上限约 2000 TPS（持锁 0.5ms）；Redis 单节点约 10 万 OPS。

任务（四步，按序做）：

  1. 热点识别表：列出这条链路上的 3 个热点（热接口、热行、热 key），每个写「峰值是多少、单点上限是多少、所以会怎样」。
  2. 库存方案：选一种（原子扣减 / 分段库存 / Redis 预扣 / 队列串行），写清吞吐上限、超卖如何避免、「假售罄」或数据不一致如何处理。
  3. 拒绝策略：在哪个环节拒绝（网关 / 队列 / 库存），拒绝比例大约多少，被拒用户看到什么。要求给出「队列有界」的具体长度与理由。
  4. 写 ADR 6（题目：秒杀场景的高并发与热点治理）：五部分齐全，后果必须含负面项（假售罄、用户被拒、Redis 与 DB 对账、运维复杂度）。
自检清单（写完逐条勾）
  • 每个热点都给出了峰值与单点上限的具体数字吗？还是只说「很高」？
  • 库存方案的吞吐上限算出来了吗？5 万 QPS 与 2000 TPS 的差距靠什么填？
  • 「不超卖」和「不假售罄」能同时保证吗？不能的话，你牺牲了哪个、怎么向用户解释？
  • 队列是有界的吗？长度是按「允许的等待时间 × 处理速率」算的，还是拍脑袋？
  • 拒绝发生在入口还是收进来之后？有没有浪费已完成的工作？
  • ADR 的负面后果里，有没有写「一部分用户必然抢不到」与「Redis 与数据库需要对账」？
参考思路（先自己写完再看）

① 热点识别——热接口：下单入口 5 万 QPS；假设单实例并发上限 560、单请求 700ms，按 Little's Law 得 560 ÷ 0.7 ≈ 800 TPS（该值需压测替换），差约 60 倍 → 必须在入口限流；热行：库存单行 2000 TPS（按持锁 0.5ms 估算），5 万 QPS 差 25 倍 → 单行必成瓶颈，必须分段或预扣；热 key：商品详情缓存单 key 打满单个缓存节点 → 本地缓存 + 多副本 key。

② 库存方案——推荐 Redis 预扣 + 异步落库：Redis 单节点 10 万 OPS，扛住 5 万 QPS；用 Lua 脚本把「判断 + 扣减」做成原子操作，不超卖；扣减成功后写入「预扣成功」队列，由消费者异步写数据库。吞吐上限由 Redis 决定。代价：Redis 与数据库存在短暂不一致（预扣了但订单还没落库）；Redis 宕机可能丢预扣，需要用数据库库存 + 订单表做对账；「预扣成功但后续下单失败」要有释放机制（超时未支付回补库存）。若不想引入 Redis，退而求其次用分段库存：1000 件拆 20 段 × 50，吞吐约 20 × 2000 = 4 万 TPS，仍不足 5 万 → 必须叠加入口限流；代价是「某段售罄、总量还有」的假售罄。

③ 拒绝策略——三道闸门：网关按用户维度限流（每人 1 次/秒），超出直接返回「活动太火爆，请稍后再试」；队列长度按「允许等待 2 秒 × 消费能力 2000 TPS = 4000 条」设定，满了立即拒绝；库存扣减失败（已售罄）返回明确失败。预期拒绝比例：10 万人抢 1000 件，至少 99% 会被拒绝——这是设计目标，不是故障。被拒用户看到的是明确的「已抢完/太火爆」，绝不能静默超时。

④ ADR 6 摘要——上下文：5 万 QPS vs 单行 2000 TPS、假设的单实例 800 TPS，差 25–60 倍（后者需压测验证）；允许部分用户失败，但不允许超卖与宕机；秒杀流量是短时尖峰，不能按峰值长期扩容。决策：入口按用户限流；库存用 Redis Lua 原子预扣，异步落库；预扣成功进入有界队列（4000 条），满了拒绝；超时未支付自动释放预扣；商品详情走本地缓存 + 多副本 key；数据库库存与 Redis 定时对账。后果——正面：扛住 5 万 QPS、不超卖、系统不被尖峰拖垮；负面：绝大多数用户会被明确拒绝；Redis 与 DB 存在秒级不一致，需对账与释放机制；分段/预扣会带来「假售罄」或「预扣成功但下单失败」；限流与队列参数需要压测调优，否则误拒真实用户；多了一套 Redis 高可用与运维成本。质量属性——性能↑（扛住尖峰）、可用性↑（拒绝优于雪崩）、一致性↓（Redis 与 DB 最终一致）、成本↑（额外组件与常态冗余）。
