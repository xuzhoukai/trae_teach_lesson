# 背景

订单服务已有 ADR 1–4。当前订单库是单实例 PostgreSQL，主从异步复制，未分片。
业务给出的数字：订单表 3 年约 6 亿行；峰值下单写入 800 TPS；峰值订单查询 5000 TPS（S1 要求 P99 ≤ 200ms）；单条订单详情约 2KB；历史订单查询占比约 30%。
用户路径：下单成功 → 跳转订单详情；用户也可能在「我的订单」列表里翻最近 3 个月的订单。

**补充前提（来自实际业务）：C 端只能查询最近 3 个月的订单；更早的订单由商家/客服线下处理。**

# 我最初的方案

| 方案     | 能不能解决  | 原因                                      |
| ------ | ------ | --------------------------------------- |
| 索引治理   | 不能完全解决 | 单表数据量过亿后，索引的性能会受影响                      |
| 读写分离   | 不能完全解决 | 可以缓解，但是单表过亿数据筛选性能差                      |
| 归档冷热分离 | 可以解决   | 将大量历史数据迁移到冷库，降低单表数据量，在索引合适的情况下可以完成目标    |
| 垂直分离   | 不能解决   | 垂直分离只适合做某个字段比较大，但是查询列表时可以不查，只在明细时查询可以有效 |
| 水平分离   | 可以解决   | 按订单时间拆分，进行分表，降低了单表数据量提升了性能              |

优化顺序：索引治理、归档冷热分离/水平分离

读一致性

索引治理，无一致性问题

读写分离有一致性问题，可能出现，主库写完，查询从库还没有同步完成的情况

归档冷热分离无一致性问题

水平分离无一致性问题

# 参考方案（修订版：C 端仅可见 3 个月）

## 0. 前提决定方案

「用户只能看 3 个月」意味着**所有 C 端查询天然带时间边界**，最多扫 3 个月的数据。这与「用户能查全部历史」是两种完全不同的访问模式，结论也不同：

- 若查询无时间边界（要看全部历史）→ 按 `user_id` 分片更合适；
- 若查询永远带时间边界 → **按月分区更简单、更便宜**。

本方案属于后者。

## 1. 容量

```
年增长：6 亿 ÷ 3 年 = 2 亿行/年
单月：2 亿 ÷ 12 ≈ 1667 万行，× 2KB ≈ 33 GB/月
在线 3 个月 ≈ 100 GB
```

结论：**单实例 PostgreSQL 可控，不需要分布式中间件。**

## 2. 排除方案（修正版）

| 方案 | 结论 | 原因 | 新增的成本 |
| --- | --- | --- | --- |
| 索引治理 | **必做** | 让高频查询走覆盖索引、避免回表。B+ 树过亿只多一层 I/O，不会让索引失效；真正拖慢的是缺复合索引与随机回表 | 无 |
| 读写分离 | **必做** | 5000 TPS 查询大部分走副本，主库只留写入与关键读 | 复制延迟 → 读己之写（见 §6） |
| **按月分区** | **推荐，本次核心手段** | 单分区 33GB、查询自带时间边界、归档即 `DROP`、扩容即加分区 | 跨月分页；分区裁剪依赖查询条件 |
| 垂直拆分 | 可选 | 详情大字段外置，降低行宽，提升列表查询与缓存效率 | 无（仍同库，本地事务） |
| 按 `user_id` 分片 | **不需要** | 3 个月可见的约束下，跨用户查询已被产品规则排除；引入分片只会增加复杂度 | 跨分片查询、全局 ID、跨分片事务 |

> 「归档冷热分离」在本方案里不是独立一步：**按月分区本身就实现了冷热分离**——旧分区 detach 后迁冷库或直接丢弃。

## 3. 存储方案：PostgreSQL 原生按月分区

```sql
CREATE TABLE orders (
    order_id    bigint      NOT NULL,
    user_id     bigint      NOT NULL,
    merchant_id bigint      NOT NULL,
    status      smallint    NOT NULL,
    amount      numeric(12,2),
    detail      jsonb,
    created_at  timestamptz NOT NULL,
    PRIMARY KEY (order_id, created_at),
    UNIQUE (order_id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_202610 PARTITION OF orders
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

三个实现要点：

1. **逻辑上仍是一张 `orders` 表**，应用层 SQL 不用改，查询自动做分区裁剪，不需要手写 `UNION ALL`。
2. **PostgreSQL 的分区表要求唯一约束包含分区键**，所以主键要写成 `(order_id, created_at)`，不能只写 `order_id`。订单号本身是全局唯一的，因此不影响业务，但 DDL 必须这样写。
3. **归档**：`ALTER TABLE ... DETACH PARTITION` 后迁冷库，或直接 `DROP TABLE orders_202601`；都比 `DELETE` 干净，且不产生 vacuum 压力。

## 4. 必须补的五个口子

1. **按订单号查详情**：分区裁剪只在 `WHERE` 带 `created_at` 时生效。按订单号查必须能定位到分区——订单号中编码月份（如 `202610` 前缀），或维护 `order_id → 月份` 映射。否则会扫全部分区。
2. **分区键语义固定为下单时间**：订单状态更新（`PENDING → PAID → SHIPPED`）回原分区那一行，不迁移分区；但「按支付时间查」会跨分区，这类查询要么改成按下单时间，要么走数仓。
3. **跨月分页**：3 个分区各取 `offset+limit` 再归并，翻页越深越贵。改用游标分页（`created_at + order_id` 作为游标），并限制最大页深。
4. **月分区自动创建**：定时任务在每月提前建好下月分区，并加「下月分区是否存在」的告警；漏建会导致当月写入直接失败。
5. **全局唯一 ID**：跨分区自增会重复，使用雪花 ID 或号段服务；订单号中同时编码分区月份，一举两得。

**商家维度的查询**：商家查「最近一个月」同样带时间边界，走同一套分区即可；在每个分区内建 `(merchant_id, created_at)` 复合索引。

## 5. 这个方案绑在一条产品规则上（必须写进 ADR）

```
产品规则：C 端只能看 3 个月
      ↓ 支撑
架构选择：按月分区，最多扫 3 个分区
```

**一旦产品放开可见窗口，方案就要重评。** 触发条件写清楚：

- 可见窗口 > 6 个月（跨分区数量翻倍）；
- 出现大量「不带时间条件」的查询（分区裁剪失效，退化为扫全部分区）；
- 单个分区写入 > 3000 TPS 或单分区容量接近实例上限。

满足任一条 → 重新评估为派生读模型（数仓 / 搜索引擎 / 按 `user_id` 分片）。

## 6. 读一致性：按读路径分别定

| 读路径 | 方案 | 可容忍延迟 | 理由 |
| --- | --- | --- | --- |
| 下单成功 → 跳订单详情 | **读主库**（或带写入 LSN 等待副本追平） | **0** | 确认页读到旧数据会被理解成「下单失败」，引发重复下单 |
| 我的订单列表（近 3 个月） | **读只读副本** | 数秒 | 列表按时间倒序，缺最新一条不会造成误操作 |
| 订单状态字段 | **不缓存** | — | 变更频繁且要求即时可见 |
| 商品详情（读多写少） | 外部缓存 + 软/硬 TTL | 分钟级 | 容忍旧数据；缓存故障时用本地缓存兜底或限流，不直接回源打库 |

**监控**：复制延迟、读主请求占比、分区裁剪命中情况（执行计划里是否出现全分区扫描）、每分区行数与容量。

## 7. ADR 5 的写法提示（这步留给你写）

- **上下文**：在线 6 亿行 / 1.2TB；峰值查询 5000 TPS、P99 ≤ 200ms；主从异步复制；历史查询占 30%；**C 端仅可见 3 个月（产品约束，方案成立的前提）**。
- **决策**：索引治理 + 读写分离 + PostgreSQL 按月原生分区；订单号编码月份；确认页读主、列表读副本；暂不按 `user_id` 分片；旧分区 detach 后迁冷库。
- **后果（必须含负面）**：
  - 不带时间条件的查询会退化为扫全部分区（靠订单号编码月份兜底）；
  - 跨月分页需要归并，深分页成本高；
  - 每月需自动建分区，漏建会直接导致写入失败；
  - 分区键固定为下单时间，「按支付时间」类查询需另建读模型；
  - 方案与「3 个月可见」强绑定，产品规则变化时需要重做存储架构。
- **质量属性**：性能↑（S1）、可用性↑（副本分担）、一致性↓（列表秒级陈旧）、可维护性↓（分区运维 + 产品约束耦合）。
