# 第 7 课练习：秒杀场景的高并发与热点治理

## 背景

单品库存 1000 件；活动开始瞬间 10 万人同时点击，入口峰值 5 万 QPS；预期 1 秒内售罄。
要求：不超卖、系统不宕机；允许一部分用户明确失败。

已知约束：

- 库存是数据库中的一行，单行更新上限约 **2000 TPS**（按持锁 0.5ms 估算）。
- Redis 单节点约 **10 万 OPS**。
- 下单链路含库存扣减与支付受理（ADR 2/3），单请求约 700ms。

---

## 【1】热点识别表

| 热点 | 峰值 QPS | 单点上限 | 结论 |
| --- | --- | --- | --- |
| **热接口**：下单入口 | 5 万 | 假设单实例并发上限 560、单请求 700ms，按 Little's Law 得 `560 ÷ 0.7 ≈ 800 TPS`（**需压测替换**） | 差约 **60 倍** → 入口必须限流/排队，扩容补不上 |
| **热行**：同一 SKU 的库存行 | 5 万 | 单行约 **2000 TPS**（`1 ÷ 0.5ms`） | 差 **25 倍** → 单行必成瓶颈，必须分段或预扣 |
| **热 key**：商品详情缓存 | 5 万 | 单缓存节点约 3 万 OPS（连接数受限） | 差约 **1.7 倍** → 需本地缓存 + 多副本 key |

> 判据只有一句：**单点上限 × 1 是否 ≥ 峰值 QPS**。小于，加机器无效。

---

## 【2】库存方案：Redis Lua 原子预扣 + 异步落库

**为什么不用分段库存**：1000 件拆 20 段 × 50，吞吐约 `20 × 2000 = 4 万 TPS`，仍低于 5 万，还得叠限流；且会出现「某段售罄、总量还有」的假售罄。

**吞吐上限**：Redis 单节点 10 万 OPS > 5 万 QPS，留 2 倍余量。

**如何不超卖**：判断与扣减放在同一个 Lua 脚本里，原子执行。

```lua
-- KEYS[1] = sku:1001:stock
if tonumber(redis.call('GET', KEYS[1])) >= 1 then
  redis.call('DECR', KEYS[1])
  return 1
else
  return 0
end
```

**完整链路**：

```
请求 → 网关限流 → Redis 预扣
                    ├─ 失败（返回 0）→ 直接返回「已抢完」
                    └─ 成功（返回 1）→ 写有界队列（4000 条）
                                    → 消费者创建订单 + 数据库原子扣减兜底
                                    → 15 分钟内未支付 → 回补 Redis 与数据库
```

**假售罄 / 不一致如何处理**：

- 预扣成功但后续下单失败 → **回补库存**，用户侧表现为「稍后可能还有」，不是永久少一件；
- Redis 宕机导致预扣丢失 → 用 **数据库库存 + 订单表定时对账** 校准；
- 数据库保留 `UPDATE ... WHERE stock >= n` 的原子扣减，作为最后一道防超卖。

---

## 【3】拒绝策略

| 位置 | 规则 | 理由 |
| --- | --- | --- |
| **网关（第一道）** | 每用户 1 次/秒；全局令牌桶按后端能力设定（约 4 万/秒） | 在入口拒绝最便宜，不浪费已完成的工作 |
| **队列（第二道）** | 有界 **4000 条** = 允许等待 2 秒 × 消费能力 2000 TPS | 队列长度必须算出来；满了立即拒绝 |
| **库存（第三道）** | 预扣失败 → 返回「已抢完」 | 明确失败，不允许静默超时 |

**预期拒绝比例**：10 万人抢 1000 件，至少 **99%** 被拒。这是设计目标，不是故障。

用户看到的内容：

- 售罄：**「已抢完」**
- 被限流：**「活动太火爆，请稍后再试」**

绝不允许「页面一直转圈」—— 那会让用户重复点击，把 5 万 QPS 变成 15 万。

## 【4】ADR 6

```
# ADR 6：秒杀场景的高并发与热点治理

## 状态
已接受（Accepted），2026-10-29

## 上下文
单品库存 1000 件，活动开始瞬间 10 万人参与，入口峰值 5 万 QPS，预期 1 秒售罄。
现有约束：库存单行更新约 2000 TPS；下单链路单请求约 700ms；Redis 单节点约 10 万 OPS。
业务要求：不超卖、系统不宕机，允许一部分用户明确失败。
假设：单实例下单能力约 800 TPS（并发上限 560 × 700ms），该值需压测验证。

四组冲突的力：
1. 5 万 QPS 与单行 2000 TPS 相差 25 倍，而所有请求竞争同一行，横向扩容无效。
2. 「不超卖」要求强一致，「扛住峰值」要求把判断前移到内存，两者方向相反。
3. 秒杀是短时尖峰，按峰值长期扩容成本不可接受，只能用限流与拒绝削峰。
4. 库存前移到 Redis 能提升吞吐，但引入 Redis 与数据库的不一致，以及宕机丢数据的风险。

## 决策
我们将对秒杀链路实施以下措施：
入口按用户限流（每人 1 次/秒），并设全局令牌桶，上限按后端处理能力设定；
库存采用 Redis Lua 脚本原子预扣（判断与扣减在同一脚本内完成），预扣成功写入有界队列（4000 条），
由消费者异步创建订单并执行数据库原子扣减兜底；预扣后 15 分钟未支付则回补库存；
商品详情使用本地缓存与多副本 key 分摊单 key 压力；Redis 与数据库、订单表定时对账；
被拒请求返回「已抢完」或「活动太火爆」，不允许静默超时。

## 后果
正面：入口可扛住 5 万 QPS；不超卖；尖峰不会拖垮下单与支付链路；成本按活动弹性投入。
负面：至少 99% 的用户会被明确拒绝，这是设计目标但需要业务方接受；
Redis 与数据库存在秒级不一致，宕机时预扣可能丢失，需依赖对账修复；
预扣成功但最终下单失败的订单会短暂占用库存，回补前其他用户可能抢不到；
队列有界意味着高峰期会误拒一部分本可成功的请求；
限流与队列参数依赖压测调优，参数失准会放大误拒或积压；
新增 Redis 高可用与运维成本，且秒杀流量与日常流量需做隔离，否则会互相影响。
中性：活动结束后需清理 Redis 中的 SKU key；预扣量与落库量的差值需要长期监控。

## 质量属性
促进：性能 ↑ —— 入口限流 + Redis 预扣，5 万 QPS 不直接打到数据库。
促进：可用性 ↑ —— 主动拒绝优于整体雪崩，下单与支付链路保持可用。
牺牲：一致性 ↓ —— Redis 与数据库最终一致，需要对账与回补。
牺牲：成本 ↑ —— 额外 Redis 集群、常态冗余与一套对账任务。
```

---

## 这道题最容易被扣分的三处

1. **没算 25 倍 / 60 倍的差距**，直接写「用 Redis 解决」。机制不等于方案，先证明它能填上差距。
2. **队列长度拍脑袋**：写「10 万条」却不解释。正确写法是 `允许等待时间 × 消费速率`。
3. **不敢写「99% 用户被拒」**：这是秒杀最真实的负面后果。只写「提升用户体验」的 ADR，评审时会被问穿。

## 数字口径（写 ADR 时必须区分）

| 类型 | 能否直接用于决策 | 本练习中的例子 |
| --- | --- | --- |
| 给定需求 | 可以，且不可改 | 10 万人、1000 件、5 万 QPS |
| 假设参数 | 可以，但必须标「假设 + 需验证」 | 单实例并发 560、单行持锁 0.5ms、单实例 800 TPS |
| 压测实测 | 最可靠，优先使用 | 实际单实例 goodput、实际单行 TPS |

需要记住的不是「60 倍」这个具体数，而是 **差一到两个数量级、且加机器补不上**。倍数会随假设漂移，量级不会。
