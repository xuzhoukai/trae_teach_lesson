# ADR 5：订单库的存储与读一致性策略

## 状态

已接受（Accepted），2026-10-29

## 上下文

订单服务已按 ADR 1–4 完成拆分、最终一致、容错与可观测性建设。当前订单库是单实例 PostgreSQL，主从异步复制，未做分区。

现有事实：

- 订单表 3 年约 6 亿行，单行约 2KB，数据量约 1.2TB（索引另计）。
- 峰值下单写入 800 TPS；峰值订单查询 5000 TPS，S1 要求 P99 ≤ 200ms。
- 历史订单查询约占全部查询的 30%。
- **产品规则：C 端只能查询最近 3 个月的订单，更早的订单由商家与客服线下处理。**

存在四组互相拉扯的力：

1. 数据量与查询性能冲突。单表持续增长会让索引与缓存效率下降，但水平分片会引入跨分片查询、全局唯一 ID 与跨分片事务，成本不可逆。
2. 归档效率与在线可用性冲突。历史数据占 30% 的查询，却与在线数据争抢同一份 I/O 与缓存；用 `DELETE` 清理会产生大量 vacuum 压力，用迁移则存在双写与切换窗口。
3. 读写分离与读己之写冲突。把查询挪到副本能承接 5000 TPS，但异步复制意味着用户可能读不到自己刚下的订单。
4. 产品约束与架构选择强耦合。「只能看 3 个月」使所有 C 端查询天然带时间边界；一旦这条规则放开，现有存储结构需要重做。

约束与假设：

- 订单状态会在原分区内的同一行上更新（`PENDING → PAID → SHIPPED → DONE`），不做跨分区迁移。
- 数据库版本支持声明式分区（`PARTITION BY RANGE`）。
- 订单号由全局唯一 ID 生成（雪花或号段），不使用跨分区自增。

## 决策

**索引治理先行。** 我们将在分区前先建立 `(user_id, created_at DESC)` 与 `(merchant_id, created_at DESC)` 复合索引，并让高频列表查询尽量走覆盖索引，减少回表。判断依据是执行计划中的扫描页数与回表次数，而不是表的总大小。

**按月原生分区。** 我们将把 `orders` 改为按 `created_at` 的 `RANGE` 分区，每月一个分区，逻辑上仍是一张 `orders` 表，应用层 SQL 不做改动。保留最近 3–4 个在线分区；更早的分区 `DETACH` 后迁入冷库，或按合规要求直接 `DROP`。

**订单号编码月份。** 订单号中编码下单月份（如 `yyyyMM` 前缀 + 雪花序列），使「按订单号查详情」能够直接定位分区，不依赖全分区扫描。分区表的主键与唯一约束写成 `(order_id, created_at)`，以满足分区表唯一约束必须包含分区键的数据库要求。

**分区运维。** 由定时任务在每月提前创建下月分区，并对「下月分区是否存在」设置告警；漏建分区会直接导致当月写入失败。

**读写分离与读一致性。** 「下单成功 → 跳转订单详情」强制读主库（或按写入位点等待副本追平），可容忍延迟为 0；「我的订单列表（近 3 个月）」读只读副本，可容忍数秒延迟。订单状态字段不进入缓存；商品详情等读多写少的数据可使用带软/硬 TTL 的外部缓存，缓存故障时以本地缓存兜底或限流，不直接回源压库。

**暂不按用户分片。** 在当前产品约束下不引入 `user_id` 分片。重新评估的触发条件为：C 端可见窗口超过 6 个月；出现大量不带时间条件的查询导致分区裁剪失效；单分区写入超过 3000 TPS 或单分区容量接近实例上限。

**监控。** 采集复制延迟、读主请求占比、每次查询的分区裁剪数量（执行计划中是否出现全分区扫描）、各分区行数与容量。

## 后果

正面：

- 常规查询只裁剪到 1–3 个分区，扫描页数约为全表方案的数十分之一，S1 的 P99 ≤ 200ms 可达成。
- 归档退化为 `DETACH` / `DROP PARTITION`，秒级完成且不产生 `DELETE` 带来的 vacuum 压力。
- 扩容只需新增下月分区，不需要 rehash 与数据迁移；单实例即可承载，无需引入分布式中间件。
- 冷热数据物理分离，旧分区可迁至低成本存储，在线库容量可控。

负面：

- 不带时间条件的查询（如按订单号查、按支付时间查）无法裁剪，会退化为扫描全部分区；前者靠订单号编码月份兜底，后者必须另建读模型。
- 跨月列表查询需要归并多个分区并做全局排序，深分页成本随页深增长；必须改用游标分页并限制最大页深。
- 每月分区自动创建一旦遗漏，当月写入会直接失败；分区数量、命名与保留策略都需要持续运维。
- 分区表的主键必须包含分区键，DDL 受限；后续若调整分区键，等于重建表。
- 「下单后详情」读主会持续给主库带来读压力，主库容量需按「写入 + 确认页读」核算，而不是只按写入核算。
- 副本延迟在高峰会造成列表短暂缺少刚下的订单；该窗口无法消除，只能监控与接受。
- 迁往冷库的数据查询需要额外路由，迁移期间存在双写与切换窗口。
- 方案与「C 端仅可见 3 个月」强绑定：产品规则一旦放开，分区数量、跨分区归并、深分页与订单号定位都会同时恶化，存储架构需要重做。

中性：

- 客服与商家的历史订单查询继续依赖线下流程，系统能力与业务流程形成耦合；该流程变化时需要同步评估存储方案。
- 分区裁剪是否生效依赖查询写法，需要在代码评审与监控中持续保障，否则性能会悄悄退化。

## 质量属性

促进：性能 ↑ —— 常规查询裁剪到 1–3 个分区，扫描页数大幅下降（S1 达标）。

促进：可用性 ↑ —— 只读副本承接大部分查询，主库只承担写入与确认页读。

促进：成本 ↓ —— 旧分区迁至低成本存储，在线库容量与缓存压力可控。

牺牲：一致性 ↓ —— 列表查询存在数秒级复制延迟窗口，可能缺少刚下的订单。

牺牲：可维护性 ↓ —— 分区自动创建、保留策略、冷库迁移都需要持续运维；方案与产品约束强耦合。
