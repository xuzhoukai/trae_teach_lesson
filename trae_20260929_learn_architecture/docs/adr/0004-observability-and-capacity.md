# ADR 4：可观测性与容量基线

## 状态

已接受（Accepted），2026-10-28

## 上下文

S1（峰值 5000 TPS 查询、P99 ≤ 200ms）、S2（单可用区故障 30 秒内切换、下单成功率 ≥ 99.9%）、S5（1 秒内给出明确结果）都已是可验收的场景。但当前线上只有进程存活与 CPU 利用率两类数据：进程是绿的，用户却可能已经拿不到结果；CPU 不满，goodput 可能已经在下降。也就是说，三条场景目前**无法被验证**。

存在四组互相拉扯的力：

1. 保护机制与监控口径冲突。ADR 3 的熔断与限流、以及负载卸载，会**故意拒绝**一部分请求。这些拒绝在成功率指标上与真实故障无法区分；若不区分，保护机制正常工作时会被当成故障，运维将长期处在误报中。
2. 容量信号与保护机制互相掩盖。服务接近过载时 goodput 先于 CPU 下降；而负载卸载一旦生效会压住 CPU，基于 CPU 的自动扩缩因此收不到扩容信号，系统会长期停在「靠拒绝请求维持」的状态。
3. 追踪深度与成本冲突。trace 能回答「卡在哪一步」，但要定位偶发问题就需要保留错误与慢请求的完整链路；采样率越高、保留越久，存储与链路后端成本越高。
4. 指标精度与基数冲突。把 order_id、user_id 放进指标标签能直接下钻到单笔订单，但每个取值都会生成一条时间序列，指标系统会被打爆。

约束与假设：

- 服务用 Go 与 Java 两种语言实现，需要跨语言一致的口径。
- 消息中间件支持在消息头透传上下文。
- 可用区余量会显著抬高常态成本：按 S1 峰值与单实例 goodput 计算，必需 7 台，考虑一个可用区失效后仍承载全量则需 11 台，常态利用率约 64%。

## 决策

**采集标准。** 我们将统一使用 OpenTelemetry SDK 采集，并以 OTLP 导出；不自建埋点格式。具体要求：

1. 追踪上下文跨进程透传：HTTP 使用 W3C `traceparent`，消息队列把上下文写入消息头，确保异步回调链路不断链。
2. 延迟类指标一律使用直方图，bucket 固定为 50/100/200/500/1000/3000ms；不使用平均值作为验收口径。
3. 指标标签使用白名单：`service`、`route`、`status_class`、`channel`、`result_type`；禁止把 `order_id`、`user_id` 等高基数字段放入指标标签，这类信息只进 span attributes 与日志。
4. 日志使用结构化 JSON，必带 `trace_id`、`span_id`、`order_id`、`error_class`；`error_class` 只允许 `retryable` / `non_retryable` / `unknown` 三个值。
5. 采样采用头部 10% + 尾部保留：所有错误请求与耗时超过 1 秒的请求全量保留，其余按 10% 采样。
6. 保留期：原始指标 90 天、降采样聚合指标 1 年、trace 7 天、日志 30 天。

**三条 SLI。** 统一采用 good / total 形式，窗口为告警 5 分钟、SLO 30 天：

- **S1 性能**：`count(查询请求 2xx 且耗时 ≤200ms) ÷ count(查询请求 2xx)`，失败请求不计入分母；服务端为主口径，客户端 RUM 为第二口径。
- **S2 可用性**：`count(下单请求返回 order_id 且未因系统错误被拒) ÷ count(下单请求，排除客户端参数错误 4xx)`；以订单终态中「归因于系统失败」的 CANCELLED 占比做交叉校验，两者需对得上。
- **S5 容错**：`count(耗时 ≤1000ms 且 result_type ∈ {success, explicit_failure, accepted_pending}) ÷ count(全部下单请求)`；`result_type` 固定为 `success` / `explicit_failure` / `accepted_pending` / `timeout_no_result` 四值，仅最后一类算不达标。

**告警分级。** 告警只基于 SLI，不以 CPU 等资源指标作为主指标：

- **page**：下单成功率（5 分钟窗口）< 99%，且窗口内下单请求数 ≥ 200。owner 为订单服务 on-call，第一步依次查看下单接口 P99 与 `timeout_no_result` 占比、库存与支付受理的超时率、熔断器状态，以区分下游真故障与阈值误触发。
- **ticket**：`WAITING_PAYMENT` 订单占比连续 1 小时 > 2%，且该小时下单量 ≥ 1000。owner 为支付服务团队，第一步按渠道拆分回调延迟与查单失败率。

**容量核算。** 容量按压测得到的单实例 goodput 计算，不按 CPU 利用率计算：基本台数 = 峰值需求 ÷ 单实例 goodput 并向上取整；再按「任一可用区失效后仍能承载全量」放大。按 5000 TPS 与单实例 800 TPS 计算，基本需求 7 台，总量 11 台，分布 4/4/3。

**错误预算。** 30 天口径的 99.9% SLO 对应允许 43.2 分钟不可用。

## 后果

正面：

- S1/S2/S5 从「口头目标」变为可计算、可告警、可复盘的指标，验收不再依赖感觉。
- 跨服务排障有了固定路径：指标发现异常 → trace 定位到具体 span → 日志看该 span 的错误详情。
- 容量成为可验算的数字，且单可用区故障时的容量已被提前覆盖。

负面：

- 指标基数与 trace 存储带来持续成本；标签白名单会限制临时下钻，遇到需要按订单排查时只能走 trace 与日志，查询更慢。
- 头部 10% 采样意味着非错误请求大多没有完整链路；偶发的慢请求若未超过 1 秒阈值，仍可能采不到，「没采到」与「没发生」难以区分。
- 告警阈值与 SLO 口径不一致是有意为之，但这意味着**page 未触发时 SLO 仍可能在缓慢恶化**，需要靠 ticket 与 30 天看板兜住。
- 阈值需要持续调优：最小请求数设得过高会漏报短时故障，设得过低会频繁误报；误报会迅速摧毁 on-call 对告警的信任。
- 可用区余量使常态利用率降到约 64%，这部分算力在多数时间里是闲置成本。
- SLI 的定义一旦调整，历史数据不可直接比较，SLO 的达成率会出现断点。
- 服务端测量的 SLI 可能达标，而用户因网络或客户端问题仍然觉得慢；第二口径（RUM）补上了这个缺口，但也引入了新的数据源与维护成本。
- 尾部采样需要额外的链路后端组件，它自身也需要高可用与容量规划。

中性：

- 每条告警都需要一个 owner 与一段可执行的第一步动作，这条要求会随服务数量增长而增加维护负担。
- `error_class` 的三值分类需要随新错误码出现持续维护，否则未知错误会被错误归类。

## 质量属性

促进：可观测性 ↑ —— 三条 SLI 直接对应 S1/S2/S5，且 trace 能定位到具体 span。

促进：可用性 ↑ —— 故障发现时间从「用户投诉」缩短到分钟级；一个可用区失效时容量已被覆盖。

促进：性能 ↑（保护侧）—— 按 SLI 触发负载卸载与限流，避免延迟问题演化为可用性问题。

牺牲：成本 ↑ —— 指标与追踪存储、尾部采样组件、以及 36% 的常态闲置算力。

牺牲：可维护性 ↓ —— 标签白名单、`error_class` 分类、告警阈值都需要持续维护与调优。
