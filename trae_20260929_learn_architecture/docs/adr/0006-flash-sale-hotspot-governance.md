# ADR 6：秒杀场景的高并发与热点治理

## 状态

已接受（Accepted），2026-10-29

## 上下文

单品库存 1000 件，活动开始瞬间 10 万人参与，入口峰值 5 万 QPS，预期 1 秒内售罄。业务要求：不超卖、系统不宕机，允许一部分用户明确失败。

现有约束：

- 库存是数据库中的一行，单行更新上限约 2000 TPS（按持锁 0.5ms 估算）。
- 下单链路单请求约 700ms（库存扣减 + 支付受理，见 ADR 3）。
- Redis 单节点约 10 万 OPS。

假设：单实例下单能力约 800 TPS（并发上限 560 × 700ms），该值需压测验证；若实测值更低，入口限流阈值需同步下调。

存在四组互相拉扯的力：

1. 5 万 QPS 与单行 2000 TPS 相差 25 倍，而所有请求竞争同一行数据，横向扩容无法分散压力。
2. 「不超卖」要求一致性与原子性，「扛住峰值」要求把判断前移到内存，两者的实现方向相反。
3. 秒杀是短时尖峰，按峰值长期扩容在成本上不可接受，只能靠限流与拒绝削峰。
4. 库存前移到 Redis 能提升吞吐，但引入 Redis 与数据库的不一致，以及 Redis 故障时预扣丢失的风险。

## 决策

我们将对秒杀链路实施以下措施。

**入口限流。** 网关按用户维度限流（每人 1 次/秒），并设置全局令牌桶，阈值按后端实测处理能力设定；超限请求直接返回明确失败，不进入下游。

**库存原子预扣。** 库存采用 Redis Lua 脚本完成「判断 + 扣减」，两个动作在同一脚本内原子执行，避免超卖；单节点 10 万 OPS 相对 5 万 QPS 留出约 2 倍余量。

**有界排队与异步落库。** 预扣成功的请求写入有界队列（容量 4000 条，按「允许等待 2 秒 × 消费能力 2000 TPS」计算），由消费者异步创建订单并执行数据库原子扣减作为第二道防超卖；队列满时立即拒绝，不无限积压。

**库存回补。** 预扣成功后 15 分钟未完成支付，释放预扣并回补 Redis 与数据库库存。

**读侧分摊。** 商品详情使用本地缓存与多副本 key 分摊单 key 压力；订单状态不做缓存。

**对账。** Redis 预扣量、数据库库存与订单表定时对账，校正由宕机或回补失败造成的差异。

**对外行为。** 被拒请求返回「已抢完」或「活动太火爆，请稍后再试」，不得静默超时。

**考虑过但未采纳：** 仅用数据库原子扣减（`UPDATE ... WHERE stock >= n`）。它不会超卖，但单行上限约 2000 TPS，无法承接 5 万 QPS；也考虑过分段库存，20 段约 4 万 TPS 仍不足峰值，且会产生「某段售罄、总量还有」的假售罄。

## 后果

正面：

- 入口可扛住 5 万 QPS，尖峰不会直接打到数据库。
- 不超卖：Redis 脚本原子扣减 + 数据库原子扣减双重兜底。
- 秒杀流量与日常链路隔离，活动不会拖垮下单与支付。
- 成本按活动弹性投入，不需要为短时尖峰长期扩容。

负面：

- **至少 99% 的用户会被明确拒绝**。这是设计目标而非故障，但需要业务方提前接受并准备对外话术。
- Redis 与数据库存在秒级不一致；Redis 宕机时预扣可能丢失，只能依赖对账修复，期间可能出现短暂少卖或多卖风险。
- 预扣成功但最终下单失败的订单会短暂占用库存，在回补前其他用户可能抢不到。
- 队列有界意味着高峰期会误拒一部分本可成功的请求；参数偏紧则误拒多，偏松则积压。
- 限流与队列参数依赖压测调优，参数失准会放大误拒或导致队列积压。
- 新增 Redis 集群的高可用、容量与运维成本，并多出一套对账任务。
- 秒杀链路与日常链路共用服务时，仍需按舱壁隔离资源，否则活动流量会挤占日常请求。

中性：

- 活动结束后需要清理 Redis 中的 SKU key，否则残留预扣会影响下一次活动。
- 预扣量与落库量的差值需要长期监控，作为数据质量指标的一部分。

## 质量属性

促进：性能 ↑ —— 入口限流 + Redis 预扣，5 万 QPS 不直接落到数据库（单行 2000 TPS 的瓶颈被绕开）。

促进：可用性 ↑ —— 主动拒绝优于整体雪崩，下单与支付链路在活动期间保持可用。

促进：成本 ↓（相对方案）—— 不需要按 5 万 QPS 长期扩容数据库。

牺牲：一致性 ↓ —— Redis 与数据库只能最终一致，依赖对账与回补。

牺牲：成本 ↑（绝对投入）—— 额外 Redis 集群、常态冗余与一套对账任务。

牺牲：体验 ↓ —— 绝大多数参与者会收到明确拒绝。
