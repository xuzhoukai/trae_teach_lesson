# 已掌握按业务能力拆分；ADR 三节串位，可用性箭头未按链路计算

用户在第 2 课练习中<b>独立</b>把订单单体按业务能力切成 5 个服务（订单 / 支付 / 库存 / 通知 / 优惠券），没有掉进「按技术分层拆」的陷阱，并且识别出「单体里可以用一个本地事务保证一致性」这一真实张力——说明服务边界与「拆分是换购」的概念已经能用。同时他把 ADR 的五部分结构照着套了下来，格式意识建立。

证据与缺口（来自 2026-09-29 第 2 课练习的原始输出）：

- **ADR 三节串位**：方案（「下单先调库存校验、再调支付」）写进了上下文；优缺点写进了上下文；缓解措施（重试、幂等）写成了后果；后果只列正面；决策句无主语（「采用拆分方案」）。说明他还没把「上下文＝冲突的力 / 决策＝我们做什么 / 后果＝会发生什么」三者分开。
- **可用性标注为「降低，增加网络开销」**：把性能代价误记为可用性代价。拆分对可用性的真实账是双面的——故障隔离 ↑、同步依赖数 ↑ 导致端到端成功率按乘积衰减。需要引入「4×99.9% 串联 ≈ 99.6%」这类算式。
- 未按任务要求建立「服务 ↔ 质量属性场景」的对应；按该标准检查，**优惠券服务没有任何场景支撑其独立**，属于无依据拆分——他尚未形成「拆分必须被要求逼出来」的检查习惯。
- 未做第 3 步反向验证。

Implications：第 3 课（跨服务一致性）开头需用 5 分钟重讲 ADR 三节分工（并强调「措施 ≠ 后果」），随后引入依赖乘积算式。此后所有拆分类练习必须<b>先交「服务 ↔ 场景」对照表，再写 ADR</b>，否则他仍会先给出结构、后补理由。
